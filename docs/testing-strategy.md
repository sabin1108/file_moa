# SDD·TDD와 테스트셋 운영 제안

## 현재 실행과 계획의 구분 — 2026-11-13

현재 실제 기능의 단위·통합 테스트와 격리 브라우저 회귀를 실행하고 있다. 아래 초기 12개 시나리오는 당시 제안한 계약이며, 현재 테스트 전체가 아직 시안이라는 뜻이 아니다. `pnpm check`는 Prisma schema·타입·린트·Vitest·서버/기능 경계·빌드를 검사한다. 브라우저·S0 그래프·실제 DB/RLS·공급자·운영 응답은 포함하지 않으므로 별도 실행 근거를 남긴다. [이번 수정 결과](verification/audit-data-preservation-20261113/README.md)는 실패 테스트 → 수정 → 재실행과 미검증 범위를 구분한다.

2026-11-08 정식 전송 경계: LT-S01~06의 변경/취소/인증/중복/한도 실패를 먼저 고정하고 구현했다. 추가 데이터는 테스트 안에서 직접 만든 짧은 MD/TXT와 기존 합성 OPFS이며 seed 난수 데이터셋이나 의미 정확도 정답셋을 새로 만들지 않았다. 기존 holdout/평가 원문을 공급자 입력으로 사용하지 않았다. 공급자/세션/DB 대체 검사와 실제 production 비로그인/Origin 거부를 구분한 [결과](verification/live-ai-transfer/README.md)를 따른다. 실제 개인 문서 모델 호출이나 새 청구 검증은 하지 않는다.

## 단계와 단위
SDD는 명세 기반 개발로 해석한다. 다른 의미를 의도했다면 용어와 계약을 수정한다.
명세(사용자 결과·예외·금지 부작용) → Given/When/Then → 필요한 실패 테스트 → 최소 구현 → 리팩터링 순서.
초기 문서 작성 당시에는 시안 단계였다. 아래 12개 시나리오는 당시 제안한 테스트 계약이며, 그 자체를 실행해서 통과한 제품 테스트로 세지 않는다.
TDD는 업무 규칙·파서·상태 전이·파일 계획·권한에서 먼저 적용한다. 사소한 문구/CSS를 확인하는 테스트를 양산하지 않는다.
운영에 적용할 함수가 없는데 수백 개의 skip/TODO 테스트를 생성하지 않는다.

## 무엇을 구해야 하는가
| 영역 | 확보 방법 | 정답/판정 |
| --- | --- | --- |
| 파일 정리 | 직접 만든 임시 폴더와 작은 MD/TXT, seed 기반 파일명/경로/충돌 조합 | 실행 전후 경로·hash·원본 보존·journal, 취소/부분 실패 |
| UI/접근성 | 합성 대화/긴 한국어/빈 목록/선택 상태/키보드 작업 | 사용자 흐름과 상태 보존, 자동 검사 + 수동 읽기 |
| 인증/job | A/B 가상 사용자와 장애 주입 | 접근 차단, 멱등성, lease/fencing, 삭제 상태 |
| 한국어 검색/RAG | 직접 쓴 작은 근거 문서 + KLUE MRC 같은 공개 QA 후보 | 근거 위치·기대 사실·답변 불가·금지 주장 |

제품 고유 파일 관리/권한 데이터는 공개 QA 벤치마크로 대체할 수 없다.
원본 개인 폴더를 긁어모아 테스트하지 않는다. 동의한 자료도 비식별·권한·보존·공개 범위를 확인한다.

## 추천 크기
1. 처음 5–15개: 사람이 검토한 핵심 회귀셋. 지금 cases.seed.json에 12개 계약 초안.
2. 기능별 50–100개: 실제 발견한 회귀 + 경계값/오류를 추가.
3. 800–1,000개: 규칙과 seed로 변형을 생성하고 실패를 작은 반례로 축소. 데이터/연산/시나리오 중 무엇을 센 것인지 명시.
예시 1,000개 배분(초기 권고): 파일·경로·충돌 300, 검색/근거 300, 격리·취소·재시도 250, UI 상태 150.
이는 1,000개 브라우저 E2E나 1,000회 유료 모델 호출을 매 PR에서 하라는 의미가 아니다.
PR은 빠른 core/단위·통합, nightly는 대량 seed 조합, E2E는 대표 10–20개 흐름부터. 실제 LLM 평가는 예산이 있는 별도 작업으로 실행한다.

## 후보와 적용 판단
- fast-check: https://fast-check.dev/docs/introduction/
  TypeScript property-based testing에 적합. 예: 복사는 입력 hash를 바꾸지 않음, 거부된 계획은 원본/대상을 바꾸지 않음, 재실행으로 중복 없음.
  재현 seed/반례/생성기 버전을 보관한다. 이번에는 제안만 하며 의존성을 추가하지 않았다.
- KLUE MRC: https://github.com/KLUE-benchmark/KLUE
  한국어 문서·질문·답 근거의 보조 후보. 문서 지식 질의 품질에 사용하고 개인 노트/파일 정리 품질로 일반화하지 않는다.
  라이선스: https://github.com/KLUE-benchmark/KLUE/blob/main/License.md 및 실제 배포 버전/출처별 조건 검토 후 채택. 이번에는 다운로드하지 않았다.
- Ragas testset generation: https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/
  보유 문서에서 single/multi-hop 질문을 만드는 보조 도구 후보. 생성된 정답을 그대로 golden으로 채택하지 않는다.
  한국어 검토, 인용 원문 대조, 답할 수 없는 질문과 공격 문서를 별도 포함. 모델/비용/문서 외부 전송을 확인한 뒤 사용.

## 표본의 품질과 누수 방지
case_id/spec_id/layer/source/license/version/fixture/expected/forbidden/split/seed를 기록한다.
문서 단위와 문서 계열 단위로 dev/holdout을 나눠 같은 문서의 질문을 양쪽에 섞지 않는다.
중복/거의 같은 문장 반복으로 개수를 채우지 않는다. 짧은/긴/한글/공백/유니코드/빈/동명/권한 철회 등 층별 커버리지를 본다.
AI 생성셋은 사람이 검토한 core와 구분하며, 같은 모델의 생성·채점만으로 통과를 주장하지 않는다.
파일 작업은 정확한 상태/불변식, RAG는 근거 회수/인용 정확/환각/응답 불가를 구분한다.
정답 없는 UI 취향이나 장시간 눈의 편안함을 자동 점수 하나로 판정하지 않는다.

## 현재 시안과 실제 기능의 경계 — 2026-10-24
이 절이 위의 일반 검증 지침보다 우선한다. 사용자 요청에 따라 기능 없는 정적 시안은 기능·회귀·부하·LLM 평가·Lighthouse 실행 대상에서 제외한다. 디자인 편집에는 타입·린트·빌드와 화면 확인만 한다. 기존 domain 테스트와 과거 Lighthouse 기록은 보존하되 이번 시안 검증 결과로 다시 인용하지 않는다.
실제 기능을 시작할 때부터 명세와 테스트를 함께 준비한다. 제품 전체 완성 뒤 일괄 테스트를 시작한다는 뜻이 아니다. 순수 규칙·권한·파서는 작은 실패 테스트부터 구현하는 TDD, 전체 사용자 흐름은 동작하는 기능이 연결된 시점에 통합/E2E로 검증한다.

### 가장 먼저 준비할 자료
| 실제 착수 기능 | 작은 자료 | 초기 확인 결과 |
| --- | --- | --- |
| 폴더 연결·읽기 | 직접 만든 임시 폴더 2개, 하위 폴더, MD/TXT 각 몇 개 | 경로/목록 일치, 거부/철회, UTF-8 오류, 원본 hash 불변 |
| 다중 선택·이동 계획 | 같은 이름·다른 내용·깊은 경로·자기 하위 이동 예시 | source/target 정확, 충돌 차단, 실행 전 원본 무변경 |
| 채팅 입력·스트림 | 긴 한글, IME, 나뉜 SSE chunk, 중단/오류 이벤트 | 중복 전송 없음, 파싱·중지·초안 보존 |
| 검색과 근거 | 사람이 작성한 문서 5–10개와 질문·근거 위치 | 답변 가능/불가, 인용 근거, 다른 workspace 자료 노출 없음 |

5–15개는 처음 구현한 기능의 대표 성공·실패 사례 수다. 현재 12개 계약을 실제 구현 없이 통과 처리하지 않는다.
800–1,000개는 핵심 규칙이 생기고 실패 분포가 보일 때 seed 조합으로 확장한다. 파일 1,000개를 읽는 성능 fixture, 1,000개 정합성 사례, 1,000개 RAG 질문, 1,000명 동시 접속은 서로 다른 단위다.
실제 계정/노트 대신 합성 자료부터 시작하고 발견한 버그를 작은 재현 자료로 회귀셋에 추가한다.

사이트 전체 측정 시점·경로/공통 자원 수치표는 [performance-policy.md](performance-policy.md), 전후 비교 양식은 [performance-record-template.md](performance-record-template.md)를 사용한다.

## 실행 가능한 대화 요청 평가셋 — 2026-11-07

`tests/fixtures/classification/request-evaluation.json`은 request-v2에서 개발용 40요청/공개 84문서와 유보용 4요청/기존 비공개 후보 8문서를 분리한다. 12개 일상 의도 유형의 도우미 후보이며 사용자 빈도 조사 결과가 아니다. 모든 기대값은 합성 자료에 대한 초안으로 사람 검토 전이다. 지원하지 않는 요청 후보 6개는 실제 검사/모델 품질 분모에서 제외한다. 오프라인 44요청/102검사와 새 실모델 6요청의 실행 결과·재현 명령은 [확장 검증 기록](verification/everyday-evaluation-cleanup/README.md)을 따른다. 최초 request-v1 기록도 보존한다.

검사는 입력 범위 안의 필수 일치·보류 ID가 제한된 후보에 남는지와 응답 판정기가 잘못된 결과를 잡는지로 나눈다. 일치 대상이 없는 요청은 recall 분모에서 제외하고, 후보에 무관한 문서가 남는 것은 허용한다. 최종 모델의 의미 판단·보류 이유 품질은 별도 실제 호출로 평가한다. 유보 문서를 이용해 후보 함수를 튜닝하지 않으며 앱 번들·공개 정적 자원·서버 카탈로그·프롬프트에 유보 문서나 기대값을 포함하지 않는다.

후속 `request-wording-variants.json`은 기존 scope/정답을 유지하는 12개 표현 변형이며 후보 회수 검사와 모델 의미 이해를 구분한다. 사람의 제품 기준 확인과 개별 44개 기대값 승인도 별도로 관리한다. [근거 검토·실패 평가](verification/expectation-review/README.md)에 날짜 의미 질문, 기간 밖 자료 오보류 실패, 지침 v4 재검증을 남겼다. 최종 v4의 한 요청을 이전 v3 전체의 재평가로 세지 않는다.
