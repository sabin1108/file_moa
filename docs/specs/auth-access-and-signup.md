# 인증 접근 제어·가입 입력·소셜 로그인

2026-11-06 최신 운영 정정: 사용자는 카카오 KOE205와 콘솔의 이메일 권한 없음/닉네임 사용 안 함을 확인한 뒤 카카오를 일시 제외했다. 현재 신규 OAuth·수단 연결은 Google/네이버만 등록한다. 저장된 Kakao provider 식별자/계정/유효 세션 인식은 보존하고 미연결 설정 행은 숨긴다. Google은 같은 이메일 계정의 자동 병합을 계속 막고, 기존 계정에서 명시적으로 연결하면 같은 모아 계정으로 사용할 수 있다. 사용자는 실제 Google 연결 성공을 확인했다.

## 2026-11-06 최신 정정 · 가입 후 표시 이름과 밝은 문서 바탕

- 이메일 가입 입력은 이메일 → 비밀번호·확인이다. Stepper·Enter/Tab/blur·IME·복원 계약은 유지하며 기존 `step=name`과 이전 초안은 이메일 단계로 안전하게 전환한다. 새 가입 초안에는 이메일·단계만 보관한다.
- AUTHPROFILE-001: 신규 이메일 계정은 이름 없이 생성하고 이메일 확인·직접 로그인을 거친 다음 `/account`에서 이름 하나를 입력한다. 이름이 빈 사용자가 작업 경로를 열면 이 화면으로 이동한다. 이미 이름이 있는 기존·소셜 사용자는 재입력을 강제하지 않는다. 이름은 공백 제거 후1~40자, 서버 세션 본인에게만 SDK로 저장한다. Origin·인증·요청 제한을 유지하고 사용자 ID·이메일·검증 상태 등 추가 필드는 거부한다. 실패하면 입력 화면을 유지한다. 이름을 이메일에서 유추하거나 가짜 기본 이름으로 채우지 않는다. 기존 String 컬럼의 빈 문자열을 미입력 상태로 사용하므로 DB migration은 없다.
- AUTHPAINT-001: 문서의 초기 HTML/CSS 바탕과 로딩 바탕을 밝게 맞춰 페이지 교체 시 어두운 문서 canvas가 드러나지 않게 한다. 사용자가 지목한 비로그인 홈 이동은 guest AuthShell의 홈 링크를 로그인으로 바로 연결해 불필요한 `/`→`/login` 왕복을 없앤다. `/` 직접 접근의 서버 인증 차단은 유지한다. 유효한 화면의 배경 재검증은 가리지 않으며 전역 loading 경계를 다시 추가하지 않는다. 초기 프레임의 computed background와 실제 차단 로딩을 검사하고 운영체제/GPU의 모든 깜빡임이 해결되었다고 확대하지 않는다.

아래 과거 이름→이메일 입력 요구와 이름 초안 보관은 이 정정으로 대체한다. 비밀번호·메일 토큰의 비보관, 메일 인증과 소셜 보안 경계는 그대로다.

2026-11-06 후속 정정: 소셜 인증의 신원과 연락 이메일 소유 확인을 분리한다. 이메일/비밀번호 가입은 인증메일이 필요하지만, 소셜 인증을 마친 사용자에게 같은 절차를 강제하지 않는다. 최신 실행 증거는 [소셜·설정 검증](../verification/auth-social-settings/README.md)을 따른다.

## 사용자 확정 범위

- 실제 회원가입의 일반 오류를 실행 근거로 진단하고 입력/메일/DB 실패를 구분한다. 비밀값·메일·토큰·원문 요청은 로그에 기록하지 않는다.
- 한 장의 폼에 이름 → 이메일 → 비밀번호·확인 입력이 순차적으로 나타난다. 각각 별도 단계이며 유효한 값의 Enter·다음 버튼·포커스 이동으로 진행한다. 이전 입력은 남는다. IME 조합 중에는 진행하지 않는다.
- Tab으로 다음 입력을 펼치면 새 입력에 초점이 이어지며 Shift+Tab은 이전 입력으로 이동한다. 폼 위쪽은 고정하고 추가 입력은 짧은 높이/불투명도 전환으로 나타낸다. reduced motion에서는 전환을 생략한다. 비밀번호/확인에는 값 변경·저장·전송 없는 보기/숨기기를 제공한다. 인증메일 대기 단계에는 처음 가입 폼으로 되돌리는 링크를 두지 않는다.
- 공통으로 재사용하는 것은 `WorkflowStepper` 표시/ARIA/CSS다. 가입 단계 상태와 URL 전이는 인증 기능이 소유한다. 종이 접힘·폴더 이동 애니메이션은 후속이며 이번에 구현하지 않는다.
- 가입 복원 URL에는 단계만 보관한다. 이름·이메일 초안은 만료가 있는 브라우저 저장소에 보관해 창을 닫아도 이어간다. 비밀번호/확인·개인정보를 복원 URL에 넣지 않으며 비밀번호/토큰은 영속 저장하지 않는다. 메일 인증·OAuth의 최초 프로토콜 링크는 별도이며 메일 토큰은 화면 초기화 후 주소창에서 제거한다. URL 단계 위조로 필수 입력/서버 인증을 건너뛰지 못한다.
- 비로그인 사용자는 실제 `/`, `/files`, `/settings`, `/account`에 접근할 수 없다. 로그인된 사용자의 `/login`, `/welcome`, 비밀번호 찾기/재설정 진입은 작업 영역으로 돌려보낸다. 소개 페이지는 아직 만들지 않는다.
- 검증된 서버 세션의 user/workspace만 폴더 owner로 사용한다. 기존 개발 owner의 자료는 자동 이관/삭제하지 않는다. 로그아웃/만료/계정 전환/다른 탭에서 현재 연결과 늦은 작업을 정리한다.
- Google·Naver·Kakao 실제 OAuth를 연결한다. 공식 로그인 버튼 자산을 로컬에 보관한다. 동일 이메일 자동 병합 금지, 미검증/미제공 이메일·취소·state 변조·중복 callback·외부 redirect를 검증한다. 공급자 콘솔의 callback/동의 설정은 소스 구현 완료와 구분한다.

## 실패 조건과 검증

- AUTHACCESS-001: 쿠키 없음·위조·만료·다른 계정의 workspace 요청을 서버에서 거부한다. 로그인 상태에서 guest 경로에 직접 URL/새로고침/뒤로 가기로 접근해도 차단한다. 프록시 헤더나 URL userId를 신뢰하지 않는다.
- AUTHACCESS-002: 사용자 A의 owner/폴더 상태가 사용자 B에게 보이거나 늦은 picker/읽기/쓰기 결과가 새 owner에 게시되지 않는다. 다른 탭 로그아웃/만료를 감지하고 접근이 불명확하면 작업 UI를 노출하지 않는다.
- AUTHSIGNUP-001: 잘못된 이름/이메일로 단계가 진행되지 않는다. Enter/버튼/blur가 중복 전이하지 않고 IME Enter가 전송하지 않는다. URL/F5/창 재열기 복원과 저장소 차단을 검증한다.
- AUTHSIGNUP-002: 비밀번호·토큰과 서버 결과를 URL/영속 저장소에 기록하지 않는다. 성공/로그아웃/초안 만료 시 정리한다. 서버가 전체 payload를 다시 검증한다.
- AUTHSOCIAL-001: 시작 endpoint/공급자 허용 목록과 고정 callback만 사용한다. OAuth state/서명 쿠키/Google PKCE 보호를 유지한다. 설치된 Kakao/Naver provider에 PKCE가 있다고 주장하지 않는다.
- AUTHSOCIAL-002: 이메일 누락/기존 이메일 충돌/취소/변조된 state/외부 callback은 계속 거부한다. 연락 이메일이 미확인이어도 SDK의 유효한 세션과 허용된 provider의 해당 사용자 바인딩이 있으면 접근을 허용하며 emailVerified를 허위로 바꾸지 않는다. 이메일/비밀번호의 미확인 계정은 세션이 생성되지 않는다. access/refresh 토큰은 서버 DB에서 암호화하고 콜백 후 ID 토큰은 저장하지 않는다.
- AUTHSOCIAL-003: 설정에서 로그인한 사용자가 명시적으로 소셜 계정을 연결/해제할 수 있다. 다른 이메일도 명시적 연결은 가능하지만 기존 다른 사용자 계정은 옮기거나 합치지 않는다. origin·최근 유효 세션·현재 사용자 귀속·요청 제한을 검증하고, 해제는 DB 잠금으로 직렬화해 실제 설정된 provider 또는 유효한 비밀번호 계정 하나 이상을 남긴다. 소셜 전용 계정은 비밀번호 재설정으로 credential이 추가되지 않는다.
- AUTHACCESS-003: 서버가 검증한 초기 화면을 재검증 때문에 숨기지 않는다. focus/pageshow/visibilitychange 중복은 하나로 합치고 현재 화면은 유지한다. 명시적 다른 계정/로그아웃·만료·확정적 무효 세션은 즉시 정리한다. 세션/쿠키의 요청 간 캐시는 추가하지 않는다.
- AUTHERROR-001: 일반 응답과 운영 진단은 안전한 오류 분류만 제공한다. 입력/메일 수신자·DB URL/비밀번호·인증/소셜 토큰·세션 쿠키는 출력하지 않는다.

검증 순서는 실패 회귀 → 단위 → 타입/린트/경계 → production build → 격리 SQL/메일/OAuth/브라우저다. 실제 외부 OAuth 콘솔 연결과 운영 회원가입·메일 수신은 별도 검증 상태로 보고한다.

2026-11-06 후속: 가입 진입의 방법 선택·공통 로딩·설정 전환과, 두 기존 계정의 명시적 접근권 연결은 [추가 계약](auth-account-connection.md)을 따른다. User/Account/Workspace 소유권은 이전하지 않으며 실제 세션 UID와 선택한 로컬 Workspace owner를 구분한다.
