# 정식 사용·테스트 사용 구조

작성일: 2026-11-07

상태: 정식/테스트 두 구조의 계약과 로컬 샘플 사용 흐름·가상 자료 Gemini 연결 구현. 정식 개인 파일 AI와 일반 PDF/XLSX 분석은 후속이며 전체 두 모드 기능 완료를 의미하지 않는다. [최신 Gemini 증거](../verification/sample-gemini/README.md).

2026-11-07 추가 범위: 정식 사용은 TXT·MD 중심으로 진행하고 PDF·엑셀의 일반 문서 지원은 후속으로 둔다. 테스트 사용의 준비된 샘플에는 PDF·엑셀도 포함한다. 사진·이미지 분류와 스캔/OCR은 이번 범위에서 제외한다. [분류 계약](ai-classification.md)·[샘플 테스트셋](../../tests/fixtures/classification/README.md)에 이어 [`/demo` 샘플 진입·세션·탭 저장소·공통 화면 연결](sample-workspace.md)을 로컬 production에서 검증했다. 운영 배포는 하지 않았다.

## 1. 공통 기능과 분리 경계

하나의 코드베이스에서 두 사용 구조를 제공한다. 파일 목록·선택·목적지 탐색·계획 검토·실행 결과·복구의 공통 책임은 재사용하고, 진입 세션·허용 작업·자료 저장소를 분리한다. 별도 앱 두 개나 같은 화면의 복사본을 기본안으로 만들지 않는다.

| 항목 | 정식 사용 | 테스트 사용 |
| --- | --- | --- |
| 주체 | 인증된 사용자와 접근이 확인된 작업 공간 | 테스트 전용 세션과 그 세션에 배정된 샘플 공간 |
| 자료 | 사용자가 직접 연결한 TXT·MD | 버전이 고정된 가상 TXT·MD·PDF·XLSX 샘플 |
| 파일 접근 | 사용자가 허용한 폴더와 작업 권한 | 해당 테스트 공간의 샘플 저장소만 |
| AI 입력 | 선택하고 외부 전송에 동의한 최소 내용 | 사전에 정의한 샘플과 허용된 요청 범위 |
| 계획 적용 | 사용자 승인·원본 재검사·충돌·복구 계약 준수 | 동일한 검토·승인 흐름으로 샘플에만 적용 |
| 보관 | 사용자/작업 공간별 기존 보관 계약 | 테스트 공간별 격리, 초기화·만료 정책 적용 |
| 계정 작업 | 실제 세션과 소유 확인을 거치는 계정 설정 | 실제 계정·로그인 수단·작업 공간 소유 변경 차단 |
| 실패 | 실제 오류와 부분 실행 결과 표시 | 같은 실패 상태를 샘플로 재현하고 초기화 가능 |

테스트 사용은 개발자 자동화 테스트와 구분되는 사용자용 기능이다. 기존 `/preview`의 정적 디자인 시안과도 구분한다. 시안만으로 테스트 사용 구조의 동작을 완료했다고 보고하지 않는다.

## 2. 정식 사용 구조

흐름: 실제 인증 → 작업 공간 접근 확인 → 폴더 연결 → 문서 선택/열람 → AI 전송 범위 확인 → 분류 제안 → 계획 수정/검토 → 명시 승인 → 실행 결과/복구.

- 서버는 실제 인증 세션에서 주체를 확정하고 작업 공간 접근을 검증한다. 요청 본문의 사용자 ID나 작업 공간 ID만으로 접근을 허용하지 않는다.
- 폴더 핸들과 실제 경로는 기존 브라우저 로컬 경계에 둔다. 폴더 연결을 외부 AI 전송 동의로 취급하지 않는다.
- AI 결과는 제안이다. 문서 ID·허용 대상·누락/중복·형식/의미를 검증하고 기존 파일 변경 계획에 연결한다.
- 원본 변경 전 사용자 승인과 기존 재검사·충돌·journal/복구 계약을 적용한다. 새로고침이나 URL 복원으로 AI 호출·파일 쓰기를 자동 반복하지 않는다.
- API 키는 서버에서 관리한다. 호출 전 한도/예산 예약, 실패/취소 후 정산과 타임아웃을 검증한다.
- 실제 AI가 연결되지 않은 상태에서는 기능 이용 가능 여부를 명확히 안내한다. 준비된 샘플 응답을 실제 분류 결과로 반환하지 않는다.

## 3. 테스트 사용 구조

흐름: 테스트 진입 → 테스트 권한/공간 확정 → 샘플 준비 → 분류 제안 → 계획 수정/검토 → 승인 → 샘플에 적용 → 결과/복구 → 초기화.

- 방문자별 테스트 세션과 샘플 공간을 분리한다. 여러 방문자가 하나의 변경 가능한 계정·작업 상태를 공유하지 않는다.
- 서버가 테스트 세션의 허용 작업과 샘플 소유 범위를 확인한다. URL·클라이언트 플래그 변경으로 정식 권한을 얻을 수 없다.
- 샘플은 개인 자료가 아닌 가상 문서로 만든다. 초기화는 해당 테스트 공간만 대상으로 하며 원본 샘플 버전을 복원한다.
- PDF·XLSX는 실제 샘플 파일과 확인된 페이지/셀 발췌를 사용한다. 샘플 지원을 임의 업로드의 파싱·분석 지원으로 확대하지 않는다. 사진, 스캔/OCR, 구형 XLS, 매크로 파일은 이번 입력 범위에 포함하지 않는다.
- 테스트 저장소는 정식 사용의 폴더 핸들·문서·설정·이력과 분리한다. 동일 브라우저에서 두 구조를 오가도 자료를 자동 이전하거나 기존 폴더를 재연결하지 않는다.
- 정식 계정 설정·실제 폴더 연결·운영 자료 접근은 테스트 권한의 범위에서 제외한다. 화면 제한과 서버 작업 권한을 함께 검증한다.
- 샘플 상태의 보관 기간과 세션 만료·정리 정책은 구현 전에 정한다. 정리 작업은 테스트 자료만 대상으로 하며 실제 사용자 자료를 보존한다.
- 테스트 공간을 초기화하거나 새 세션을 만들어도 전체 유료 호출 한도가 초기화되지 않도록 한다. 실제 모델 호출 시 서버에서 전체 예산을 예약/정산한다.

### 분류 결과의 출처

테스트 사용 구조는 다음 두 실행 상태를 구분한다. 이는 별도 제품 구조를 추가하는 것이 아니라 같은 테스트 흐름에서 결과를 얻는 방식이다.

| 상태 | 결과 | 검증할 수 있는 것 |
| --- | --- | --- |
| 준비된 결과 사용 | 샘플 버전에 대응하는 고정 제안, 샘플 응답임을 표시 | 선택·계획 수정·승인·샘플 실행·복구의 제품 흐름 |
| 실제 모델 호출 | 서버에서 샘플을 모델에 전송한 응답 | 위 흐름과 해당 샘플에 대한 실제 모델 결과·사용량·응답 시간 |

실제 호출 실패를 고정 응답으로 조용히 바꾸지 않는다. 어떤 결과를 사용했는지 사용자가 알 수 있어야 한다. 고정 결과를 사용하는 테스트로 모델 품질을 검증했다고 보고하지 않는다.

## 4. 기존 코드에 연결할 책임

- 현재 정식 진입은 [`WorkspaceLayout`](../../apps/web/src/app/(workspace)/layout.tsx) → [`requireWorkspace`](../../apps/web/src/server/session-guards.ts) → [`SourceFolderProvider`](../../apps/web/src/features/local-folders/providers/SourceFolderProvider.tsx) 순서로 실제 세션/owner와 브라우저 연결 수명을 구성한다. 이 보호를 유지한다.
- 테스트 진입은 별도 세션/샘플 저장소를 조합한다. 구현 시 기존 서비스가 실제 폴더 핸들과 권한을 가정하는 지점을 확인하고 필요한 경계만 분리한다. 테스트 주체를 실제 사용자인 것처럼 정식 Provider에 주입하지 않는다.
- 공통 화면·Stepper·목적지 선택·계획 검토·실행/복구 규칙은 기존 책임을 확인해 재사용한다. 모드 조건을 각 버튼과 파일 처리 함수에 흩뿌리거나 범용 저장소 프레임워크를 먼저 만들지 않는다.
- 최초 문서화 단계에는 새로운 SDK·DB 테이블·라우트·운영 설정을 추가하지 않는다. 실제 세션 방식과 저장소 연결은 구현 명세에서 타입·권한·실패 조건과 함께 확정한다.

## 5. 명세와 테스트셋

명세·가상 문서·기대값·실패 테스트 초안은 도우미가 작성하고, 사용자는 대표 분류 기준과 기대 결과를 확인한다. 문서 개수와 테스트 사례 수·유료 호출 횟수를 구분한다.

- 현재 가상 MD 16개·TXT 16개·PDF 1개·XLSX 1개, 총 34개와 기대값 초안을 준비했다. 개발용 26개/holdout 8개이며 공개 후보 10개만 `/demo`에 연결했다. 분류는 준비된 제안이며 모델 정확도 평가는 아니다.
- 문서별 허용 분류·복수 정답·검토 필요·금지 결과를 기록한다. 모호한 문서에 임의로 단일 정답을 강제하지 않는다.
- 사례 ID는 `id`, 연결 명세는 `specIds`, 자료 경로는 `file`로 기록하며 `expected/forbidden/split/family`를 함께 둔다. `source/version/seed/reviewStatus`는 데이터셋 공통 메타데이터다. 개발용과 최종 평가용은 문서 계열 단위로 분리한다.
- 화면에 공개할 샘플과 앱에 노출하지 않을 holdout을 구분한다. 이 holdout은 같은 작성자가 만든 유보 자료이며, 저장소 접근자에 대한 비공개나 독립적인 블라인드 평가를 보장하지 않는다. 기대값은 사람 검토 전 초안이며 AI가 만든 정답을 같은 AI의 판단만으로 확정하지 않는다.
- 실제 함수가 연결되는 시점에 권한·파서·상태 전이의 실패 테스트부터 작성한다. 미구현 함수를 위한 대량 skip/TODO 테스트는 만들지 않는다.

아래는 실행 전 수용 기준이며 현재 통과한 테스트가 아니다.

| ID | 조건/행동 | 기대 결과 |
| --- | --- | --- |
| MODE-001 | 정식 사용에서 실제 인증과 작업 공간 접근 확인 | 허용된 사용자 자료만 접근, 미인증/범위 밖 접근 거부 |
| MODE-002 | 서로 다른 두 테스트 세션이 샘플을 수정 | 상태가 섞이지 않고 각자의 결과만 표시 |
| MODE-003 | 테스트 세션으로 정식 계정/자료 작업을 직접 요청 | 서버가 거부하고 실제 자료·설정 불변 |
| MODE-004 | 동일 브라우저에서 정식/테스트 구조 전환 | 핸들·샘플·초안·이력이 다른 구조로 넘어가지 않음 |
| MODE-005 | 제안 목적지를 수정하고 승인/취소 | 수정한 계획만 적용, 승인 전과 취소 후 파일 불변 |
| MODE-006 | 샘플 작업 일부 실패·복구·초기화 | 항목별 결과 표시, 해당 공간만 복구/초기화 |
| MODE-007 | 누락·중복·외부 대상·문서 안 지시문 포함 | 응답 검증/검토 처리, 허용되지 않은 파일 변경 없음 |
| MODE-008 | 새로고침·중복 요청·세션 만료·초기화 | 호출/쓰기 자동 반복 없음, 만료/이전 작업의 늦은 완료 차단 |
| MODE-009 | 동시에 유료 호출하거나 새 테스트 세션 생성 | 서버의 전체 예산 예약/정산 유지, 한도 초과 호출 차단 |
| MODE-010 | 고정 결과 사용 또는 실제 모델 호출 실패 | 결과 출처/실패 표시, 고정 결과를 실제 응답으로 위장하지 않음 |

## 6. 구현 순서와 완료 기준

1. 두 사용 구조의 권한·입출력·저장소 수명과 대표 샘플/기대값을 확정한다.
2. 정식 인증 경계를 유지하며 테스트 세션/저장소 격리의 실패 테스트와 최소 구현을 만든다.
3. 공통 파일/계획/실행/복구 기능에 연결하고 고정 결과로 테스트 흐름을 검증한다.
4. 실제 AI의 입출력 검증·전체 예산·취소/실패 처리를 연결해 정식/테스트 양쪽 호출 경계를 검증한다.
5. 교차 접근·초기화·새로고침·동시 요청과 실제 브라우저/키보드/좁은 화면을 검증한다. 물리 IME·Windows 권한창과 합성 저장소 검증의 범위는 따로 기록한다.

완료는 두 구조에서 해당 흐름이 실제로 동작하고, 분리·실패 경로를 실행해 확인한 상태다. 문서 작성, 정적 시안, 고정 응답 흐름, 실제 모델 평가를 각각 구분해 보고한다.
