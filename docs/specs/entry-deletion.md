# 파일·폴더 삭제 — 구현 전 계약 초안

2026-10-31. 전날 마지막 사용자 요청의 “삭제할 수 있는 방식”을 재개하며 작성했다. **설계 초안이며 삭제 기능은 아직 구현하지 않았다.** 휴지통 이동/영구 삭제 선택은 미정이다. 기록 조회와 복구 흐름을 먼저 마련한 뒤 실행을 연결한다.

## 사용자 흐름

1. 현재 폴더의 대상 선택 → 삭제 검토. 기존 파일 선택과 폴더 선택의 의미를 분명히 하고, 상위 폴더와 그 하위 항목의 중복 선택은 한 작업으로 정리한다.
2. 확인 화면에서 정확한 상대 경로·항목 종류·개수·처리 방식·복구 가능 여부를 표시한다. 하위 내용을 다 읽지 못한 폴더는 빈 폴더로 표시하지 않는다.
3. 취소를 기본 안전 경로로 제공하고 사용자의 명시적 실행에서만 쓰기 권한을 요청한다. 연결 해제는 삭제와 독립된 동작이다.
4. 항목별 완료·실패·미실행·미확인을 표시한다. 부분 실패를 전체 성공으로 묶지 않는다. 재접속 후 기록을 조회해 실제 현재 상태를 확인하며 자동 재삭제하지 않는다.

## 실행 전에 결정할 사항

| 결정 | 수용 조건 |
| --- | --- |
| 휴지통 또는 영구 삭제 | OS 휴지통 연동을 검증하기 전에는 휴지통으로 보낸다고 표시하지 않는다. 앱 내부 보관 방식을 고르면 위치·보존 기간·복원 충돌·저장 공간·정리 방식을 별도로 정한다. 영구 삭제는 되돌릴 수 없다는 확인이 필요하다. |
| 폴더 범위 | 첫 구현의 빈 폴더만 허용할지, 내용 있는 폴더까지 포함할지 정한다. 재귀 삭제를 기본값으로 숨기지 않는다. |
| 외부 변경과 경쟁 | 검토와 실행 사이 대상의 종류·핸들·내용 변경 감지 및 중단 규칙을 정한다. 브라우저 API의 실제 보장 범위를 조사하고 원자성을 가정하지 않는다. |
| 작업 기록 보관 위치 | 삭제 대상 내부에 유일한 기록을 두지 않는다. 연결 루트, `.moa-history`, 보관 폴더 자체는 일반 삭제 대상에서 제외한다. |
| 복구 | 보관본/원본/기록의 일부 실패, 재시작, 같은 이름의 새 항목, 저장 공간 부족에 대한 복구 경로를 정한다. 기존 이름을 덮어쓰지 않는다. |

## 구현 전 실패 테스트

- 권한 거부/철회, 연결 교체, 기록 저장 실패: 삭제 호출 없음.
- 미조회·부분 조회·읽기 실패 폴더: 빈 폴더 판정/일괄 성공 없음.
- 검토 후 대상 교체·내용 변경·이미 사라진 대상: 새 대상 삭제/이전 성공 재사용 없음.
- 두 번째 항목 실패·실행 중 종료: 첫 항목 결과와 나머지 미실행/미확인을 보존.
- 복원 이름 충돌·보관본 손상·공간 부족: 기존 파일 보존, 실패 원인과 수동 조치 표시.
- 대상 없음·취소·IME 조합 Enter: 쓰기 권한 요청 및 삭제 없음.

위 목록은 아직 실행한 테스트가 아니다. 다음 단계는 현재 `.moa-history` 읽기 전용 조회 → 재접속 결과 확인 → 삭제 방식 확정 및 API 보장 검토 → 실패 테스트 → 최소 실행 구현이다. 실제 복사·이동은 각각의 충돌/복구 계약에 따라 별도로 진행한다.
