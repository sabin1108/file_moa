# AI 기반 앱 개발 시 반드시 지켜야 할 개인정보 암호화 법적 기준 및 실무 가이드 (상세본)

이 문서는 유튜브 '코딩하는 기술사'의 "AI로 만든 회원가입, 암호화 기준 지키기" 영상의 내용을 바탕으로, 서비스 개발 시 반드시 지켜야 하는 개인정보 암호화의 법적 기준과 실무 가이드를 상세히 정리한 것입니다. (기준: 개인정보의 안전성 확보조치 기준 안내서 2025년 11월 최신판)

## 1. 개인정보 보호 의무 위반 시 법적 책임
AI가 코드를 짜주었다고 해서 법적 책임에서 자유로워지는 것은 아닙니다. 1인 개발자나 작은 서비스라도 예외 없이 엄격한 잣대가 적용되며, 유출 시 다음과 같은 무거운 책임을 지게 됩니다.

* 과태료 및 과징금: 안전조치 의무 위반 시 3천만 원 이하의 과태료, 유출 시 막대한 과징금 부과
* 손해배상: 피해 발생 시 손해배상 의무 발생 (고의나 중과실의 경우 최대 5배까지 가중)
* 기타 조치: 유출 발생 시 정보주체 통지 및 관계기관 신고 의무, 사안이 중대할 경우 시정명령 처분 사실 공표

### 실제 처분 사례
* 사례 1: 락앤락 (2026년 7월)
  * 원인: 이메일 서버 보안 취약점을 이용한 내부망 침입. 130만 명의 정보 유출.
  * 위반 사항: 고유식별정보 등이 암호화되지 않은 상태로 보관됨.
  * 처분: 과징금 5억 300만 원, 과태료 540만 원.
* 사례 2: 법무법인 로고스 (2025년 11월)
  * 원인: 외부 해킹으로 1.59TB 분량의 소송 자료 유출.
  * 위반 사항: 주민번호, 계좌번호, 비밀번호 등 주요 데이터가 암호화 없이 평문 저장.
  * 처분: 과징금 5억 2,300만 원, 과태료 600만 원.

결론: 해킹 방어 시스템도 중요하지만, 암호화는 정보가 유출되었을 때 2차 피해를 막는 핵심 방어막이자 법적 책임을 경감받을 수 있는 주요 장치입니다.

## 2. '암호화'와 '해싱'의 정확한 이해
민감한 정보를 보호하는 두 가지 핵심 기법은 목적에 따라 다르게 사용해야 합니다.

* 암호화 (양방향): 평문을 암호문으로 변환하고, 필요시 특정 키를 사용해 다시 평문으로 복호화할 수 있는 방식입니다. (예: 계좌번호, 주민번호 등)
* 해싱 (단방향): 평문을 해시 함수를 통해 암호화하되, 역으로 복호화가 불가능한 방식입니다. (예: 사용자 비밀번호)

## 3. 법적 필수 암호화 대상 (7대 정보)
우리 서비스에 다음 7가지 정보를 수집, 저장, 전송할 경우 법적으로 반드시 암호화해야 합니다.

[고유 식별 정보 4가지]
1. 주민등록번호
2. 여권번호
3. 운전면허번호
4. 외국인등록번호

[기타 중요 정보 3가지]
5. 신용카드 번호
6. 계좌 번호
7. 생체 인식 정보

참고사항: 이메일, 이름, 휴대전화번호도 암호화해야 할까?
법적으로 필수 의무 대상은 아닙니다. 하지만 법에서는 유출 시 위험을 고려하여 암호화하여 저장할 수 있다고 권고하고 있습니다. 암호화나 접근 통제 등 보안 조치를 추가해 두면 사고 발생 시 책임을 덜 수 있습니다.

### 전송 구간 암호화 의무
데이터베이스(DB) 저장뿐만 아니라, 사용자의 브라우저와 서버 간 네트워크 통신 과정에서도 개인정보가 전송된다면 필히 암호화해야 합니다. 웹 서비스의 경우 HTTPS 적용이 필수입니다.

## 4. 적용 대상의 구분: '이용자' vs '그 외 정보주체'
법에서는 정보주체를 두 그룹으로 나누어 암호화 기준의 엄격함을 다르게 적용합니다. 
* 이용자 (온라인 고객): 기준이 매우 엄격합니다. 인터넷망이든 내부망이든 저장 위치를 불문하고 어디에 저장하든 무조건 암호화 대상이며, 신용카드와 계좌번호가 필수 대상에 포함됩니다.
* 이용자가 아닌 정보주체 (임직원, 오프라인 고객 등): 상대적으로 적용 범위가 다릅니다.

## 5. 핵심 실무 보안 권장 사항 (Best Practices)

1) 비밀번호 해싱: SHA-256 사용 지양
* SHA-256은 데이터 무결성 검증을 위해 속도가 빠르게 설계된 범용 해시 함수입니다. 
* 위험성: 속도가 빠르다는 것은 해커가 레인보우 테이블이나 무차별 대입 공격을 통해 비밀번호를 유추해 내는 연산도 매우 빠르다는 뜻입니다.
* 해결책: KISA 등 보안 기관에서는 비밀번호 해싱 시 연산 속도를 늦춰 방어력을 높인 Bcrypt나 Argon2 사용을 강력히 권장합니다.

2) 암호화 키 분리 (하드코딩 절대 금지)
* 소스 코드 내에 텍스트 형태로 암호화 키를 직접 적어 넣는 것은 매우 위험합니다. 소스가 공개되거나 유출되면 암호화 키도 즉각 노출됩니다.
* 해결책: 암호화 키는 환경 변수 파일(.env)로 분리하거나, OS 설정, 안전한 외부 저장소를 사용하여 소스 코드와 완벽히 분리해야 합니다.

3) 개인정보 저장 최소화 (최고의 보안)
가장 확실한 보안은 애초에 위험한 데이터를 가지고 있지 않는 것입니다.
* 결제 정보: 카드번호, 계좌번호 등은 직접 DB에 저장하지 말고 결제 대행사(PG사)에 위임하여 처리하세요.
* 주민등록번호: 직접 수집하지 말고 본인확인기관(CI/DI)을 이용해 인증 용도로만 활용하세요.

## 6. AI를 안전하게 활용하는 프롬프트 엔지니어링 팁
AI를 사용할 때 단순한 기능 구현만 지시하면 보안에 취약한 코드가 나옵니다. 

* 구체적 보안 지시: "비밀번호는 Bcrypt를 써서 단방향 해싱해 줘", "암호화 키는 .env 파일에서 불러오도록 작성해 줘"라고 명확히 요구해야 합니다.
* 규칙 및 최신 법령 주입: "현재 시행 중인 개인정보 안전성 확보 조치 기준 제7조(개인정보의 암호화) 원문을 우선해서 코드를 짜줘"라고 명시하여 최신 기준을 강제하는 것이 좋습니다.

## 7. 서비스 배포 전 5대 자가 진단 체크리스트
배포 직전, 다음 5가지를 반드시 점검하세요.

- 데이터베이스에 비밀번호가 평문으로 저장되어 있지 않은가?
- 비밀번호를 다시 알아낼 수 있는 양방향 암호화(복호화)로 잘못 구현하지는 않았는가?
- 우리 서비스가 수집하는 정보 중 법적 필수 암호화 대상(7가지)이 누락 없이 암호화되었는가?
- 암호화 키, 데이터베이스 비밀번호, 외부 API 키 등이 소스 코드 어딘가에 직접 작성되어 있지 않은가?
- 개인정보가 오가는 구간이 HTTP가 아닌 HTTPS 환경으로 안전하게 전송되고 있는가?
