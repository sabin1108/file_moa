# 사용자가 강조한 개발·구조·디자인 기준

정리일: 2026-10-30 · 대상: 개인 AI·파일 관리 작업 공간

이 문서는 이전 대화의 실제 사용자 발언과 `E:\memory\chatbotfolder` 인수인계를 찾아 묶은 요구사항 목록이다. 단순히 현재 코드의 특징을 사용자 요구로 바꾸어 적지 않았다. **[직접]**은 원문 로그/현재 대화로 확인한 요구, **[기록]**은 인수인계에 보존된 기준, **[적용 해석]**은 구현 시 의미를 구체화한 설명이다. 요구가 있다는 사실과 구현·검증 완료는 별개다. 중복 대화는 합쳤고, 하위 에이전트에게 전달된 작업 지시나 자동 알림은 사용자 발언으로 인용하지 않았다.

## 1. 가장 중요한 원칙: 구조로 해결할 일을 코드로 덮지 않기

> “유지보수성과 재사용성이 높아야 하는거야 즉 구조로 해결될걸 소스코드로 해결하지 말아줘” — [직접, D:402]

1. **책임 경계를 먼저 정한다.** UI, 상태 변화, 업무 규칙, 파일/네트워크 접근을 한 컴포넌트에 몰아넣지 않는다. [A:219, D:402]
2. **사용자가 직접 리뷰할 수 있어야 한다.** 코드가 어디에 있고 무엇부터 읽어야 하는지 알 수 있는 구성을 만든다. [A:219, D:402]
3. **기능별로 묶고 그 안에서 역할을 나눈다.** 큰 features 폴더 하나에 기능 파일이 무질서하게 쌓이지 않게 한다. [D:1704]
4. **재사용을 고려한다.** 같은 버튼·표시·디자인·컴포넌트/함수는 반복 구현보다 일관된 사용을 우선한다. [A:689, B:972]
5. **기본적인 프로젝트 관례를 따른다.** Next의 app 구조와 실제 기능 구현 위치를 구별하고, 익숙한 components/ui/hooks/services/styles 등의 의미를 살린다. [D:1704]
6. **불필요하게 복잡한 구조도 피한다.** prototype/preview 때문에 제품 코드를 찾기 어려워지는 문제를 해결한다. [C:509, D:1704]

**적용 해석:** 조건문·호환 래퍼·중복 상태를 늘려 경계 문제를 덮기 전에 소유권, 의존 방향, 화면 포함 관계를 바로잡는다. 파일 개수나 줄 수를 맞추기 위한 기계적인 분리는 목표가 아니다. 실제 반복 근거가 없는 범용 계층을 만들라는 요청도 아니다.

## 2. 코드 설명과 읽는 순서

7. **주요 코드에는 짧고 의미 있는 주석을 단다.** 무엇을 담당하는지, 어디에서 쓰는지, 어떤 흐름으로 동작하는지 설명한다. [D:1704]
8. **당연한 문법 설명은 생략한다.** “이것은 버튼 UI입니다” 같은 주석을 모든 코드에 붙이는 것은 원하지 않는다. [D:1704]
9. **실행 시작점과 연결 흐름을 보여준다.** React의 main/App처럼 이 프로젝트에서는 어느 layout/page에서 시작하여 어떤 기능으로 이어지는지 설명한다. [D:402]
10. **변경한 파일과 리뷰 순서를 알려준다.** 기능을 구현했다는 말만 하지 말고, 사용자가 실제로 볼 파일 위치와 책임을 연결한다. [D:402, E:240]
11. **도입한 기술의 이유를 설명한다.** 프레임워크·라이브러리 목록뿐 아니라 선택 근거, SSR/CSR 구분, pnpm 사용 이유를 알려준다. [D:402, E:240]
12. **개발 환경 전용 코드를 표시한다.** localhost 임시 코드가 배포용 기능으로 오인되지 않도록 주석·가이드·코드 설명에서 드러낸다. [C:509]

현재 코드 읽기 안내는 `apps/web/src/README.md`, `features/local-folders/README.md`, `docs/code-map.md`에 있다. 이는 이번에 확인한 문서 위치이며 사용자 원문 인용은 아니다.

## 3. 웹 표준·타입·기본 원리

13. **브라우저에서 보인다고 올바른 HTML은 아니다.** 유효한 콘텐츠 모델과 웹 표준을 지킨다. [D:402]
14. **모든 것을 div로 만들지 않는다.** 역할에 맞는 태그와 속성, 기본 동작을 활용한다. [D:402]
15. **기본 원리를 지키되 보안 문제는 고친다.** 관례를 이유로 이미 발견된 보안·동작 문제를 방치하지 않는다. [D:402]
16. **TypeScript any는 정말 필요한 경우로 제한한다.** 원문은 “필요할때 아니면 지향”이라고 되어 있으나 문맥과 인수인계는 불필요한 any를 피하라는 뜻이다. [D:883, M]

**적용 해석:** `p` 안의 `div`와 상호작용 요소 중첩을 점검한다. 다만 `p` 안의 `button`을 모두 금지하는 규칙으로 일반화하지 않는다. 버튼·링크·체크박스·dialog의 본래 의미를 살리고 키보드/초점/접근 가능한 이름까지 확인한다. 외부의 불명확한 값은 `unknown`과 검증/타입 좁히기로 처리하며 타입 단언으로 검사를 우회하지 않는다.

## 4. 서버·클라이언트 책임과 보안

17. **SSR/CSR 경계를 설명한다.** 실제 파일 처리 위치와 서버에서 하는 일을 혼동하지 않게 한다. [E:240]
18. **서버 데이터 접근은 서버 경계에 둔다.** 사용자는 Next Server Actions 활용과 프론트엔드의 API 데이터 가공 금지를 강조했다. [E:240]
19. **민감정보를 브라우저에 노출하지 않는다.** API 비밀키, 토큰, DB 내부 구조와 불필요한 민감 데이터를 보호한다. [E:240]
20. **사업/업무 규칙의 책임을 화면으로 넘기지 않는다.** 데이터가 화면의 가공 로직에 의해 다른 의미로 변하는 것을 경계한다. [E:240]

**적용 해석:** 서버가 인증·인가·DB 접근·업무 판정·화면용 응답 계약을 소유한다. 클라이언트의 날짜 표시나 로컬 폴더 UI 상태 처리까지 무조건 서버로 보내는 뜻은 아니다. 브라우저에 전달한 데이터와 요청은 개발자 도구로 볼 수 있으므로 “Server Actions라서 F12에 아무것도 안 보인다”는 보장을 하지 않는다. 브라우저 로컬 폴더는 서버가 사용자의 절대 경로를 직접 읽는 구조로 바꾸지 않는다. [M, 프로젝트 경계]

## 5. SDD·TDD·검증의 책임

21. **명세와 테스트를 함께 진행한다.** SDD/TDD를 적용하는지 반복해서 확인했다. [A:689, D:293]
22. **실제 기능부터 검증한다.** 정적 시안의 기능 테스트를 과도하게 늘리지 말고 실제 동작 구현에서 검증을 시작한다. [A:947]
23. **테스트 폴더를 제품 코드와 분리한다.** 사용자는 기능 코드와 CSS를 읽으며 구조를 이해하고 싶다고 했다. [D:1704]
24. **일반적인 검사는 에이전트가 맡는다.** 테스트를 사용자에게 넘기는 것을 기본 진행 방식으로 삼지 않는다. [D:1704, 현재 대화]
25. **테스트 파일이 무엇을 검증하는지 설명한다.** test.ts의 역할과 읽는 법도 이해 가능해야 한다. [C:509]
26. **테스트셋을 설계한다.** 소규모 5–15개부터 800–1,000개 규모까지 자료를 어떻게 확보·구성할지 고민해야 한다. 숫자만 채우는 것이 목적은 아니다. [A:689]
27. **계획한 검증과 통과한 검증을 구별한다.** 시나리오 수·파일 수·데이터 항목 수를 같은 수치로 보고하지 않는다. [기록, M]

**AI 코드 리뷰에서 사용자가 직접 지정한 세 가지** [C:509]:

- 프로젝트의 실제 버전과 맞는 코드인가?
- API와 기능이 실제 존재하는가? 존재하지 않는 내용을 지어내지 않았는가?
- 테스트가 실제 동작을 검증하는가? 가짜 구현이나 테스트 자체를 검증하고 있지는 않은가?

**적용 해석:** 명세 → 실패 조건/정답셋 → 실패 재현 → 구현 → 검증 순서를 남긴다. 합성 자료는 출처와 재현 조건을 적고, API/권한 창을 대체한 fixture는 실제 OS 검증과 구분한다. 검증하지 않은 성능·보안·접근성을 완료로 표현하지 않는다.

## 6. 성능은 채팅뿐 아니라 사이트 전체

28. **전체 사이트의 성능과 수치표를 기록한다.** 사용자는 “채팅이 느려지는 것뿐 아니라 사이트 전체”라고 다시 명확히 했다. [A:1019, A:1024]
29. **기능 추가 전후를 비교한다.** 모든 기능이 끝난 뒤 한 번 측정하는 방식보다 단계별 기준선과 변화 원인을 추적한다. 기능 추가 시 기존 수치의 비교 의미도 설명해야 한다. [A:947, 기록 M]
30. **Lighthouse 등 측정 도구를 적극 활용한다.** 점수만으로 UX나 전체 제품 완료를 판단하지 않는다. [A:689, 기록 M]
31. **가독성·재사용성과 최적화를 함께 고려해 점진적으로 구현한다.** [B:972]

**기록에서 구체화된 적용 기준:** 동일 화면·자료·브라우저·권한·캐시 조건의 회귀 비교, 새 기능의 비용, 동일 기능 최적화를 구분한다. 사이트 공통 자산·경로별 로딩·상호작용·메모리·네트워크를 함께 기록한다. 측정 없이 memo/useCallback을 일괄 적용하지 않는다. Node/pnpm의 현재 버전은 환경 기록이지 사용자의 영구 버전 선호가 아니다. [M, docs/performance-policy.md]

## 7. 시각 디자인·읽기 편안함

32. **AI 템플릿 같은 인상을 줄인다.** taste 계열의 판단을 활용하되 획일적인 시안을 반복하지 않는다. [A:516, B:142]
33. **여백을 화면의 목적에 맞게 구성한다.** 작은 중앙 상자 주변이 지나치게 비는 문제를 고친다. [B:142]
34. **빈 공간을 억지로 채우지 않는다.** 모든 화면에 로그인과 같은 왼쪽 패널을 복제하는 방식도 피한다. [B:142]
35. **가로로 넓히기만 하는 해법은 거절했다.** 일괄 가로 확장 대신 간격·행 높이·조작 크기·대상 간 관계를 조정한다. [기록, M 및 현재 AGENTS]
36. **긴 대화의 눈 피로를 줄인다.** 색감뿐 아니라 글꼴·글자 크기·정보량을 함께 검토한다. [A:689]
37. **Gothic A1은 참고 후보로 제안했다.** 반드시 그 폰트로 고정하라는 결정으로 확대하지 않는다. [F:451]
38. **transition과 box-shadow는 절제한다.** 필요 없으면 쓰지 않아도 된다. [기록, M]
39. **공통 구조와 조작은 재사용하되 화면을 획일화하지 않는다.** 페이지·dialog가 다루는 실제 대상과 행동이 기준이다. [A:689, B:142, 기록 M]

## 8. 파일 관리에서 반복한 세부 UX

40. **관리·이동·복수 정리가 중심이다.** 단지 파일을 보기 위한 도구처럼 느껴지지 않게 한다. [A:689]
41. **폴더 안에 파일이 속한다는 포함 관계를 보여준다.** 파일만 나열하고 폴더/정리 도구를 눈에 띄지 않는 위치에 두지 않는다. [A:947]
42. **폴더 연결 성공 후 자연스럽게 내 파일로 이동한다.** 취소나 실패를 성공으로 오인해서 이동하지 않는다. [D:1164, 기록 M]
43. **폴더 연결 관리는 설정 아이콘의 팝업으로 제공한다.** [기록, M]
44. **마우스/브라우저 뒤로·앞으로 가기를 지원한다.** 파일 미리보기에서 돌아오거나 다시 앞으로 갈 수 있어야 한다. [F:757]
45. **처음부터 정보를 과하게 펼치지 않는다.** 검색·편집·파일 정보 같은 부가 조작은 필요할 때 드러내고 모바일에서도 확인한다. [F:757]
46. **데스크톱 사이드바와 본문 사이의 어색한 빈 공간을 점검한다.** [F:757]
47. **목적지 상대 경로를 탐색해서 고를 수 있게 한다.** [F:1056]
48. **경고는 확실히 구분하되 색상만으로 상태를 전달하지 않는다.** 경고 색상 요청과 이번 선택 UX 지적을 함께 반영한다. [F:1056, 현재 대화]
49. **‘선택/선택 취소’는 파일 선택 버튼에 대한 요구였다.** 목적지 확인 버튼만 고치는 것으로 대체하지 않는다. 체크박스, 선택 수, 취소의 결과를 명확히 한다. [현재 대화]
50. **폴더 목적지는 이름과 경로로 인식할 수 있어야 한다.** 단순한 색감 차이로만 파악하는 방식은 불편하다고 지적했다. [현재 대화]
51. **새로고침 아이콘 깨짐과 클릭 시 화면 흔들림을 고친다.** 로딩·완료 전환 때 조작 크기와 목록 위치도 확인한다. [현재 대화]
52. **이동·복사·조작 과정에서 새 폴더를 만들 수 있어야 한다.** 이번 추가 답변으로 실제 디스크 생성까지 명시적으로 선택했다. [현재 대화]
53. **폴더 관리 디자인은 이번 ZIP으로 교체한다.** `C:\Users\sabin\Downloads\최종안_시안.zip`의 데스크톱·모바일 구성을 기준으로 하며 기존 폴더 디자인 유지보다 최신 지시를 우선한다. [현재 대화]

## 9. 범위·진행·기록 방식

54. **기능을 하나씩 연결하며 점진적으로 확장한다.** 로그인은 별도로 요청할 때 구현한다. [F:451]
55. **실제 기능·정적 시안·미구현을 구별한다.** 샘플 숫자나 모형 UI가 제품 기능처럼 보이지 않게 한다. [A:249, A:947, C:509, 기록 M]
56. **불필요해진 prototype은 정리할 수 있다.** 다만 과거 설명 요청을 임의 삭제 승인으로 확대하지 않는다. [C:509]
57. **중단된 작업은 실제 로그와 파일을 확인해 이어간다.** memory에 내용을 추가하는 것으로 작업 복원을 대신하지 않는다. [현재 대화]
58. **안전하고 명확한 다음 작업은 계속 진행한다.** 매번 “진행할까요?”로 사용자가 다시 지시하게 만들지 않는다. 파괴적이거나 범위가 실질적으로 달라지는 결정은 구분한다. [현재 대화, 사용자 AGENTS]
59. **요구의 내용뿐 아니라 반영 방법과 검증 근거를 남긴다.** 무엇을 요청했고 어떤 책임 분리·테스트·수정으로 해결했는지 추적 가능하게 한다. [사용자 AGENTS, M]
60. **새 항목과 기록은 현재 들어가 있는 폴더를 기준으로 만든다.** 기록용 폴더를 다시 지정하는 창은 기본 흐름에서 필요하지 않다. [현재 대화, 직접]
61. **Windows처럼 폴더·TXT·MD를 쉽게 만들 수 있어야 한다.** 종류를 고르고 이름을 입력할 수 있게 하며 익숙하지 않은 사람도 사용할 수 있어야 한다. 확장자 자동 보완과 최종 파일명 표시는 이를 적용한 구현 해석이다. [현재 대화의 답변, 직접/적용 해석]
62. **폴더 연결 설정은 실제 폴더 작업 위치 가까이에 둔다.** 우측 상단에 있어 너무 멀고 사용성이 좋지 않다는 피드백이다. 위치 변경은 다음 작업이며 아직 미구현이다. [현재 대화, 직접]
63. **입력한 파일 확장자로 생성 의도를 반영한다.** 폴더 종류가 선택돼 있어도 `aaa.txt`를 입력하면 `aaa.txt` 파일이 생성돼야 한다. 사용자가 보고한 `aaa` 폴더 생성 현상은 다음 작업에서 재현·수정할 항목이다. [현재 대화, 직접]
64. **파일/폴더를 삭제할 수 있는 방식도 마련한다.** 삭제 기능 요구를 추가한다. 휴지통/영구 삭제, 대상 범위와 복구 방식은 아직 정하지 않았다. 이번 요청은 기록이며 실제 삭제를 수행하라는 지시가 아니다. [현재 대화, 직접/범위 구분]

후속 아이디어로 남은 항목: 마우스 좌클릭을 길게 눌러 방향별로 이동하는 원형 퀵 메뉴를 기획에 추가해 달라고 했다. 당시 즉시 구현 요청은 아니었으므로 이번 폴더 개편 완료 항목으로 세지 않는다. [A:947]
