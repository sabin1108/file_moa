# 모아 기능 구현 코드 읽기 가이드

작성 기준: 2026-10-31 현재 소스 · 프로젝트 `E:\project\ai_folder_project`

현재 구현된 로컬 폴더 기능의 구성을 읽는 안내서다. 첫 번째 읽기는 최근 수정한 **연결 설정 위치와 폴더·TXT·MD 생성**을 끝까지 따라간다. 두 번째 읽기는 기존 목록·선택·검색·미리보기·방문 기록·변경 계획으로 넓힌다. 테스트 파일과 테스트 결과는 읽기 대상에서 제외했다.

줄 번호는 작성 시점 기준이다. 코드가 바뀌면 함께 적은 함수·속성 이름을 검색한다. 처음부터 모든 import를 따라가지 말고 아래 순서로 읽는다. `Icon`, `actionClasses`, 공통 버튼 스타일은 기능 흐름을 파악한 뒤 봐도 된다.

## 1. 먼저 알아둘 코드 구성

기능 코드의 기준 폴더는 `apps/web/src/features/local-folders/`이다. 아래에서 `components/…`, `store/…`처럼 짧게 쓴 경로는 이 폴더 아래를 뜻한다.

| 위치 | 맡는 일 | 실제 예 |
| --- | --- | --- |
| `app/(workspace)/` | 라우트 진입과 공통 Provider 배치 | `files/page.tsx`, `layout.tsx` |
| `components/` | 화면 조합, 입력, 표시, 팝업, 초점 | `SourceFolderBrowser`, `NewEntryForm` |
| `providers/` | 여러 화면이 같은 연결 객체를 사용하도록 공유 | `SourceFolderProvider` |
| `hooks/` | React 수명·구독과 기능 객체를 연결 | `use-source-folder-connection` |
| `store/` | 진행 상태, 중복 요청, 늦은 결과, 선택과 탐색 상태 | `EntryCreationController`, `SourceListingController` |
| `lib/` | 파일 접근 없이 입력값으로 결과를 계산 | `resolveNewEntry`, `filterFolderEntries` |
| `services/` | 브라우저 핸들·권한·IndexedDB·파일 접근 | `connection-session`, `create-entry`, `folder-creation-journal` |
| `types.ts` | 화면과 저장소 사이 입출력 형태 | `FolderHandle`, `HandleRepository`, `FolderConnectionView` |

이 기능의 `services`는 서버 API를 뜻하지 않는다. 연결한 로컬 폴더에 브라우저가 접근하는 코드다. 파일 핸들과 연결 정보는 브라우저에 있고, 이 흐름에서 원본 파일을 서버로 업로드하지 않는다.

전체 흐름은 다음과 같다. 화살표는 주요 호출 관계이며 모든 화면 조작이 모든 계층을 거치는 것은 아니다.

```text
/files 페이지
  → SourceFolderBrowser: 공유 객체를 받아 화면과 동작을 연결
      → FolderWorkspaceFrame: 경로/상위 목록/현재 목록/미리보기 배치
      → FolderListingView: 현재 목록과 조작 표시
          → SourceFolderSettingsDialog: 연결 팝업
          → NewEntryForm: 새 항목 입력

NewEntryForm
  → resolveNewEntry: 생성할 이름과 종류 미리 계산
  → EntryCreationController.run: 진행 상태와 완료/실패 문구
      → 공유 connection.createEntry
          = FolderConnectionSession.createSourceEntry
              → createEntry: 권한/충돌 확인 후 실제 생성
                  → DirectoryFolderCreationJournal: 작업 기록 저장
  ← 성공 여부
  → onCreated()
      = listing.refresh()
          → 목록 다시 읽기 → 구독한 화면 갱신
```

### ④ 공유 객체는 어디에서 만들어지는가

- [SourceFolderProvider.tsx](E:/project/ai_folder_project/apps/web/src/features/local-folders/providers/SourceFolderProvider.tsx): **전체**, 특히 `developmentOwner`, `SourceFolderProvider`, `useSharedSourceFolderConnection`.
- [use-source-folder-connection.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/hooks/use-source-folder-connection.ts): **전체**, 특히 `useState` 초기화 → `useSyncExternalStore` → 시작/정리 effect → 마지막 return.

hook이 `IndexedDbHandleRepository → FolderConnectionSession → SourceConnectionController`를 조립한다. Provider는 이 결과를 하위 화면에 공유한다. hook 끝의 다음 연결은 꼭 확인한다.

```ts
createEntry: session.createSourceEntry
```

따라서 폼에서 보이는 `connection.createEntry`는 별도 API나 다른 구현이 아니라 session 메서드에 붙인 공개 이름이다.

`useState(() => new …)`는 렌더마다 기능 객체를 새로 만들지 않게 한다. `useSyncExternalStore`는 객체의 변경 알림을 React 렌더와 연결한다. 시작 effect는 연결 복원·지원 환경 확인을 수행하고 종료 시 controller를 정리한다.

**현재 임시 구현:** `developmentOwner`, 개발용 DB 이름, localhost 제한은 실제 로그인 전 개발용이다. 사용자 계정 인증이 구현돼 있다고 해석하면 안 된다. 교체 의도는 해당 코드의 `TEMPORARY(local-folder-dev)` 주석에 적혀 있다.

## 3. 첫 번째 읽기의 본론: 새 파일 한 개를 끝까지 따라가기

이제 화면에서 **폴더를 선택한 채 `aaa.txt`를 입력하고 만들기**를 누르는 상황으로 읽는다.

### ⑤ 입력과 제출 — NewEntryForm

[NewEntryForm.tsx](E:/project/ai_folder_project/apps/web/src/features/local-folders/components/listing/NewEntryForm.tsx): **10줄 `NewEntryForm`부터 끝까지**.

읽는 순서는 `connection` → controller 생성/구독 → `name`/`kind` → `resolveNewEntry` → form의 `onSubmit` → select/input → 최종 결과 안내다.

- `name`, `kind`는 사용자가 입력한 값이다.
- `entry`는 그 입력을 해석한 **최종 이름·종류**다. 선택값이 folder여도 입력이 `aaa.txt`면 최종 종류는 txt다.
- 입력 중 해석에 실패하면 미리보기만 생략한다. 실제 제출은 controller/service의 검증을 거친다.
- `pending` 중 재제출을 막고, 한글 조합 Enter는 제출하지 않도록 한다.
- 제출 시 `controller.run(path, name, kind)`를 호출한다.
- 성공하면 이름 입력을 비우고 `onCreated()`를 호출한다.

**다음:** 미리보기와 실행이 왜 같은 이름을 쓰는지 확인하려면 `resolveNewEntry`를 읽는다.

### ⑥ 이름과 종류를 결정하는 순수 규칙

[new-entry.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/lib/new-entry.ts): **전체 1–25줄**.

| 읽을 부분 | 확인할 내용 |
| --- | --- |
| 1–2줄 | 지원 종류와 예약 기록 폴더 이름 |
| 4–9줄 `validateName` | 경로 문자, 예약 이름, 공백/끝 점, 길이 등 이름 제한 |
| 12–21줄 `resolveNewEntry` | 선택 종류 확인 → 이름 검증 → NFC 정규화 → 명시적 확장자 우선 → 필요한 확장자 보완 → 최종 검증 |
| 23–25줄 `resolveEntryName` | 이름만 필요한 호출자를 위한 반환 형태 |

입력과 결과를 눈으로 대입한다.

| 선택 | 입력 | 최종 종류 | 최종 이름 |
| --- | --- | --- | --- |
| folder | aaa.txt | txt | aaa.txt |
| txt | 기록.MD | md | 기록.MD |
| md | 일지 | md | 일지.md |
| folder | archive.zip | folder | archive.zip |

알 수 없는 확장자를 임의의 파일 종류로 추측하지 않는다. 이 파일에는 폴더 핸들·권한 요청·실제 파일 생성이 없다.

### ⑦ 진행 상태와 결과 문구

[entry-creation-controller.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/store/entry-creation-controller.ts): **1–10줄 상태/오류 문구 → 13줄 class부터 끝까지**, 중심은 `run`이다.

`run`의 순서:

1. 이미 pending이면 중복 실행을 막는다.
2. 이번 요청의 generation을 잡고 pending을 게시한다.
3. `resolveNewEntry`로 최종 이름·종류를 얻는다.
4. 생성자에서 전달받은 `this.create(path, entry.name, entry.kind)`를 호출한다.
5. 현재 요청이면 ready와 결과 문구를 게시한다. 실패하면 오류를 화면용 문구로 바꾼다.
6. 성공/실패 여부를 폼에 돌려준다.

`publish`는 state 변경 후 listener들을 호출한다. 폼의 `useSyncExternalStore`가 이 알림을 받아 화면을 갱신한다.

`dispose()`는 generation을 바꿔 늦은 결과가 폐기된 폼에 반영되지 않게 한다. 이미 시작된 파일 쓰기를 취소하거나 되돌리는 함수는 아니다.

**다음:** `this.create`의 실체는 ④에서 확인한 session의 `createSourceEntry`다.

### ⑧ 연결의 유효성을 붙여서 실제 생성에 전달

[connection-session.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/services/connection-session.ts): 생성 흐름에서는 먼저 **205–215줄 `createSourceEntry`만** 읽는다. 필드 의미가 필요하면 **16–29줄**로 올라간다.

- 현재 owner, root 핸들, 연결 세대와 순번을 잡는다.
- 연결이 준비되지 않았으면 실행하지 않는다.
- `assertCurrent`를 만들어 연결이 교체됐는지 확인할 수 있게 한다.
- 현재 부모 경로를 담은 `DirectoryFolderCreationJournal`을 만든다.
- `navigator.locks.request("moa-folder-creation", …)`를 실제 생성 함수에 전달한다.

session은 **어느 연결에서 진행하는 작업인가**, service는 **그 연결에 무엇을 어떻게 생성하는가**를 나눠 맡는다. Web Lock은 이를 사용하는 같은 출처의 앱 작업을 조율하는 수단이며 외부 파일 프로그램의 모든 경쟁까지 막는다고 해석하지 않는다.

### ⑨ 실제 폴더·파일 생성 — 핵심 파일

[create-entry.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/services/create-entry.ts): **8–66줄 전체**를 아래 구간별로 읽는다.

| 구간 | 실행 내용 | 읽으며 볼 질문 |
| --- | --- | --- |
| 13–19줄 | 경로/최종 이름·종류 검증, readwrite 권한 요청 | 잘못된 입력이 실제 접근 전에 거부되는가? |
| 20–34줄 | lock 안에서 부모 경로 탐색과 이름 충돌 확인 | 실제 생성 위치가 현재 경로인가? 같은 이름을 덮어쓰는가? |
| 35–36줄 | pending 기록 저장 | 생성 전에 작업 의도가 남는가? |
| 38–45줄 | 부모 핸들·권한·충돌·기록 가능 여부 재확인 | 기다리는 동안 달라진 상태를 다시 확인하는가? |
| 46–53줄 | 종류에 맞는 생성 API, 재조회, 동일 핸들·빈 파일 확인 | TXT를 폴더 API로 만들지 않는가? |
| 54–58줄 | ready 기록 후 최종 상대 경로 반환 | 실제 결과 확인과 기록이 완료된 뒤 반환하는가? |
| 59–64줄 | 실패/미확인 처리 | 생성 시도 후 문제를 단순 미생성으로 오해하지 않는가? |

UI/controller에서 해석했어도 service가 다시 `resolveNewEntry`를 호출한다. 파일 접근 경계가 앞단의 검증에만 의존하지 않게 한 것이다.

빈 파일은 `getFileHandle(..., { create: true })`로 준비한다. 사용자 대상 파일에는 `createWritable`을 열지 않는다. 이미 같은 이름의 파일이 외부에서 생겼을 때 내용을 절삭하는 동작을 피한다. 생성 API가 반환됐다는 것과 새 항목을 오직 이 앱이 만들었다는 보장은 구별한다.

### ⑩ 작업 기록은 어디에 어떻게 남는가

[folder-creation-journal.ts](E:/project/ai_folder_project/apps/web/src/features/local-folders/services/folder-creation-journal.ts): **5–8줄 계약 → 11–53줄 class 전체**.

- `FolderCreationRecord`: 버전, 작업 ID, 상대 경로, kind, 상태, 시간.
- `destination()` **18–32줄**: 현재 부모 아래 `.moa-history`를 준비한다. 동일 이름 파일이 있으면 충돌 오류다.
- `assertWritable()` **33–35줄**: 기록 쓰기 권한 확인.
- `put()` **36–52줄**: 새 무작위 이름의 JSON 생성 → 내용 저장/close → 다시 읽어 저장 내용 확인.

생성할 사용자 파일은 빈 파일이지만 **작업 기록 JSON에는 내용을 쓴다.** 두 파일의 쓰기를 혼동하지 않는다. pending과 ready는 같은 작업 ID를 가진 별도 기록이며 이전 기록을 덮어쓰지 않는다. 파일명 접두사에 folder가 있어도 kind는 txt/md일 수 있다.

현재 구현은 기록을 남기는 단계다. 기록 조회 화면이나 자동 복구까지 이 파일이 수행하는 것은 아니다.

### ⑪ 생성 결과가 목록에 나타나는 마지막 구간

## 7. 읽으면서 남길 메모

각 모듈마다 아래 다섯 줄만 채워도 코드 리뷰 흐름을 유지하기 쉽다.

```text
이 파일의 역할:
받는 입력과 돌려주는 결과:
이 파일이 직접 소유하는 상태:
외부 접근이 일어나는 위치:
다음으로 호출하거나 결과를 돌려주는 파일:
```

특히 다음을 스스로 설명해 본다.

- `kind` 선택값과 최종 `entry.kind`가 다른 상황은 무엇인가?
- Form/controller/service가 공유 규칙을 사용하면서 각각 다른 책임을 가지는 이유는 무엇인가?
- 생성 controller의 generation과 session의 연결 세대는 각각 무엇을 막는가?
- 실패와 결과 미확인 상태가 구분되는 시점은 어디인가?
- 기록 저장소와 연결 핸들 저장소는 무엇이 다른가?
- 생성 성공 후 목록에 새 행을 직접 추가하는가, 다시 읽는가?

이 문서는 코드 구조를 읽기 위한 길잡이다. 코드 변경이나 종합 리뷰 판정은 포함하지 않는다.
