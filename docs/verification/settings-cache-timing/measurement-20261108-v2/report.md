# 설정 캐시의 실제 로그인 속도 비교

2026-11-08, 사용자 브라우저에서 before→after→after→before 순서로 완료한 네 번의 실행이다. 각 실행에서 작업 공간 10회·설정 10회를 오갔다. 설정 40개, 전체 화면 준비 80개 표본을 기록했다.

## 핵심 결과

반복 설정 진입의 중앙값은 **1.541초 → 0.675초**, **56.2% 감소**했다. 절약된 시간은 약 866ms다.

| 구간 | 이전 조회 방식 복원 | 현재 캐시 방식 | 시간 변화 |
| --- | ---: | ---: | ---: |
| 첫 작업 공간 진입 | 3.965초 | 6.247초 | 57.6% |
| 첫 설정 진입 | 2.887초 | 0.681초 | -76.4% |
| 첫 작업 공간 + 첫 설정 합계 | 6.852초 | 6.927초 | 1.1% |
| 반복 설정 진입 | 1.541초 | 0.675초 | -56.2% |

첫 진입의 합계는 거의 같았다. 사전 준비로 대기가 작업 공간 첫 진입으로 옮겨갔고, 이후 설정 화면에서 기다리는 시간이 줄어든 결과다. 전체 첫 진입이나 서비스 전체가 56% 빨라졌다고 해석하지 않는다.

| 순서 | 방식 | 첫 작업 공간 | 첫 설정 | 합계 | 반복 설정 중앙값 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | before | 3.999초 | 2.945초 | 6.944초 | 1.557초 |
| 2 | after | 6.293초 | 0.692초 | 6.985초 | 0.678초 |
| 3 | after | 6.200초 | 0.669초 | 6.869초 | 0.669초 |
| 4 | before | 3.931초 | 2.829초 | 6.760초 | 1.529초 |

첫 진입 지표는 방식별 2개, 반복 설정은 방식별 18개다. 반복 범위는 이전 1.524초~1.561초, 현재 0.663초~0.685초였다. 작은 표본의 p95는 참고용 원자료에만 남겼다. 모든 브라우저 표본의 너비는 1920px다.

## 서버에서 확인한 변화

설정 표시 reader 중앙값은 863.399ms → 0.277ms였다. 현재 방식은 두 번의 첫 준비에서 callback을 각각 1회 실행했고, 이후 설정 조회 20개에서는 callback 실행이 0회였다. 첫 준비 구간의 중앙값은 2264.0ms였다.

이것은 reader 호출/캐시 callback 증거이며 실제 SQL round-trip 개수는 측정하지 않았다. 인증은 계속 실행된다. readSettingsDisplay 안의 인증 시간은 같은 렌더의 memoization을 포함하므로 전체 인증 비용으로 표현하지 않는다. reader가 빨라져도 탐색·인증·렌더링 등 다른 구간이 남는다. 브라우저와 서버 시간을 빼서 네트워크 시간이라고 계산하지 않았다.

## 재현 범위와 한계

- 정확한 옛 빌드는 보존되어 있지 않아 현재 UI에 캐시 전 세션 기반 조회 방식을 복원했다. 옛 전체 버전의 실행 결과가 아니다.
- 이전은 프로필을 세션에서 얻고 현재의 cache miss에는 프로필 DB 조회가 추가된다. 사전 준비·조회 방식 변화 전체의 비교이며 캐시 API 하나만의 효과가 아니다.
- 같은 로컬 production, 실제 인증·DB, 한 사용자 브라우저다. 현재 서비스의 Vercel 속도나 사용자 집단을 대표하지 않는다.
- 각 시행 전 해당 측정 서버를 재시작하고 그 복사본의 fetch-cache만 비웠다. 원래 3034 앱은 그대로 두었다. 브라우저 HTTP 캐시는 유지했다.
- Link prefetch를 끄고 고유 query로 router.push를 실행했다. 일반 메뉴의 같은 URL·prefetch/Router Cache 탐색과 다를 수 있다.
- 서버 결과가 반영된 실제 화면의 준비를 두 frame 뒤 확인했다. 물리적 체감·LCP·INP를 직접 측정한 값은 아니다. 수집 시각은 결과가 수집기에 도착한 시각이다.
- 모델 API 키를 전달하지 않아 이번 측정의 AI 호출은 0회다. 계정 정보·쿠키·토큰·파일 본문을 측정 파일에 기록하지 않았다.
