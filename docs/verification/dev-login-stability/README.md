# 로컬 로그인 화면의 반복 로딩 복구

2026-11-09. 사용자가 로컬 로그인 화면에서 ‘화면을 준비하고 있어요.’가 계속 표시된다고 보고했다. 인증/일반 채팅 제품 코드를 바꾸지 않고 실제 개발 서버와 격리 브라우저에서 원인을 분리했다.

## 확인한 원인

서버는 `/login`을 HTTP200으로 반환했다. 반면 브라우저는 Next 개발 서버의 WebSocket에서 `reloadPage`와 `HMR hash mismatch`를 반복해서 받았다. HMR은 수정한 코드를 개발 화면에 반영하는 기능이다. 설치된 Next16.4.3의 `dist/server/dev/hot-reloader-turbopack.js`는 클라이언트가 보낸 HMR 버전이 서버 버전과 다르면 RELOAD_PAGE를 전송한다. 이 강제 새로고침 때문에 로그인 폼이 잠깐 나타나도 다시 상위 loading 경계로 돌아갔다.

계정 쿠키가 없는 새 Chromium에서도 같은 현상을 재현했으므로 특정 사용자 쿠키나 실제 로그인 시도에 의존하는 증상이 아니었다. 브라우저 예외는0건이었다. 최초에 HMR 상태가 어긋난 계기는 아직 확정하지 않았다. 바로 전 작업에서 dev 서버를 켠 채 next-env의 생성 타입 참조를 production 참조로 복원하고 Prisma 생성이 포함된 typecheck를 실행했지만, 각각을 단독 원인으로 입증하지 않았다.

## 복구와 재발 확인

작업자가 띄운3034 개발 서버만 정상 종료하고 `pnpm dev`로 다시 실행했다. Next가 생성한 `.next/dev/types` 참조를 그대로 두었다. 실행 중인 개발 서버에 맞춰 생성된 next-env 파일을 Git 차이를 줄이기 위해 수동으로 되돌리지 않는다. 이번에는 원본 파일·계정 데이터·폴더 연결·브라우저 쿠키를 삭제하거나 `.next` 전체를 지우지 않았다.

| 실제 개발 모드 검사 | 복구 전 | 복구 후 |
|---|---:|---:|
| 6초간 루트/로그인 요청 수 | 32 | 1 |
| HMR 강제 새로고침 | 27 | 0 |
| 1초 간격 로그인 폼 정상 표시 | 1/6 | 6/6 |
| 브라우저 실행 예외 | 0 | 0 |

복구 전 `tests/browser/check-dev-login-stability.mjs`가 강제 새로고침 검사에서 실패한 뒤, 재시작 후 같은 검사가 통과했다. [복구 후 원자료](after.json)는 실제 개발 서버/격리 Chromium의 관측이며 전 자료는 비공개 `.omx/dev-login-stability/before.json`에 보존했다. 개인정보·쿠키·인증 URL 값은 수집하지 않는다.

이전 일반 채팅 작업의1199개/production 검사는 이 개발 서버 안정성 검사를 포함하지 않았다. health200만으로 실제 로그인 화면의 안정성을 검증했다고 볼 수 없다. 새 회귀는 개발 모드의 실제 idle 화면에서 HMR 메시지와 폼 유지 상태를 함께 확인한다.

```powershell
node tests/browser/check-dev-login-stability.mjs http://127.0.0.1:3034
```

현재3034 서버는 새로 실행한 세션58698로 유지한다. 제품 인증/채팅 소스는 이번 복구에서 수정하지 않았으므로 전체 단위·린트·production 빌드를 반복하지 않았다. 실제 소셜 로그인·운영 계정 전체 여정·유료 모델 호출은 이번 검사에 포함하지 않는다. 서버 재시작으로 HMR 상태 불일치는 해소됐지만 Next 내부 최초 트리거를 수정한 영구 패치라고 주장하지 않는다.

후속: 로그인 화면 유지가 정상인 상태에서 실제 인증 요청은 별도 DB 네트워크 차단으로 실패했다. 같은 앱을 네트워크가 허용된 환경에서 다시 실행해 실제 이메일 거부/Google·네이버 시작 응답과 HMR0을 확인했다. 현재 실행 세션과 인증 상태는 [로컬 인증 복구 기록](../local-auth-runtime/README.md)이 우선한다.
