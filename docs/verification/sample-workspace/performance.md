# 샘플 작업 공간 성능 표본

2026-11-07, Windows·Chrome156 headless·GPU 비활성·로컬 production·CPU/네트워크 제한 없음. 폭별3회 원자료의 중앙값이다. `/files`는 비로그인 상태의 `/login` 이동이며 실제 인증된 파일 화면 측정이 아니다. 작은 표본의 p95나 실사용 INP로 해석하지 않는다.

## 기존 guest 경로 전후

같은 브라우저 프로필의 HTTP cache를 재사용하고 표본마다 새 target을 연다. 원자료: [전36표본](performance-before.json), [후42표본](performance-after.json). 후42개는 기존6경로36개와 신규 demo6개다. 기능 추가 전후의 서로 다른 빌드이며 순수 최적화 비교가 아니다.

| 경로 | 390px LCP 전→후 ms | 1440px LCP 전→후 ms | 후 CLS 최대 |
| --- | ---: | ---: | ---: |
| /login | 92→72 | 56→64 | 0 |
| /welcome | 64→56 | 52→60 | 0 |
| /forgot-password | 60→56 | 68→60 | 0 |
| /reset-password | 72→68 | 84→80 | 0 |
| /verify-email | 84→80 | 92→68 | 0 |
| /files → /login | 72→68 | 76→56 | 0 |

전체 static JS/CSS 원본 합계는 1,404,928 → 1,497,788바이트(+92,860바이트, 약90.7KiB)다. 이는 전체 배포 자산 증가이며 모든 경로의 최초 전송 증가를 뜻하지 않는다. 캐시 재사용 표본의 JS 전송 중앙값0을 JS가 없거나 제거됐다는 뜻으로 해석하지 않는다. 서버/클라이언트 캐시·실행 순서·로컬 부하에 따른 변동이 있어 속도 개선율을 주장하지 않는다.

## 신규 /demo 비용

기존 guest 경로를 먼저 지난 cache 재사용 표본의 LCP 중앙값은 390px72ms, 1440px72ms, CLS0이었다. 이 순서에서 최초 demo의 추가 JS resource 전송은67,094바이트였지만 신규 방문의 전체 cold 전송은 아니다.

따로 [HTTP cache 비활성6표본](performance-cold.json)을 측정했다. Network domain 활성화 뒤 cache를 비활성하고, 각 표본에서 JS의 실제 전송이0이 아닌지 확인했다. 앞선 준비 실행에서 domain 활성화 없이 얻은 cache 재사용 수치는 cold 결과로 쓰지 않는다. 샘플 쿠키는 이미 유효한 상태이며 세션 최초 발급 전환 전체 여정은 별도다.

| 폭 | LCP 중앙값 ms | CLS 최대 | HTML 전송 중앙값 KiB | resource 전송 중앙값 KiB | 그중 JS KiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 390 | 112 | 0 | 7.4 | 251.9 | 231.7 |
| 1440 | 108 | 0 | 7.4 | 251.9 | 231.7 |

HTML과 resource를 구분했고 원자료에는 각 round가 있다. PDF/XLSX 원본과 페이지 이미지는 선택할 때 별도 요청하는 자료로, 최초 TXT/MD 읽기 면의 수치와 혼동하지 않는다. 공개 카탈로그의 바이너리는 서버 모듈에만 두고 Client Component props에는 발췌·표·페이지 수만 보낸다.

인증 계정의 기존 파일/복구 흐름, 운영 지역 RTT·서버 RSS/부하·모델 응답·field INP·물리 GPU는 미측정이다. 로컬 인증 API503도 이 guest 로딩 값으로 정상 판정하지 않는다.
