# 이름 검색 기능의 성능 기록 — 2026-10-29

기능 추가 비용과 기존 선택 흐름 회귀를 구분한다. 동일 기능의 최적화 전후가 아니다.

## 재현 조건과 원자료

이전은 [직전 변경 계획 기능의 desktop](../file-change-plan/performance-after.json)과 [390px](../file-change-plan/performance-after-mobile.json) 최종값을 보존해 사용했다. 이번 측정은 [desktop](performance-after.json), [390px](performance-after-mobile.json)이다. 전후 모두 Chrome156.0.8078.48, Windows, production, localhost3010, CPU/네트워크 제한 없음, HTTP cache disabled, 경로별 새 탭, 로드 뒤1.2초 관찰, 6경로×3회×2폭이다. 390px는 실제 휴대전화가 아닌 데스크톱 viewport다.

검색 전 지문 `8e1beb91a36628e96b8f57bde70639ea2eb34d853832822a7f39fd068b52fcdf`. 검색 후 desktop `1d234106f846ed7a9e37c910097ae82ccdfe4e6e8fc1dddec0a741ec7849fc0c`, 390px `c3aa1ca1ae09e8924813cc4f06a8f4a2298b9ecf722406c03861c5297f540237`. 두 이후 측정 사이 기능 README를 수정했다. 측정 도구가 src 안의 Markdown까지 해시하므로 지문이 다르며, 제품 코드·서버 빌드는 바뀌지 않았고 전체 정적 자산803469bytes도 같다. 이를 별도 실행 빌드 차이로 해석하지 않는다.

로딩은 폴더 미연결 초기 화면이며 로그인/모델/API가 없다. PerformanceObserver LCP/CLS·ResourceTiming·CDP JS heap을 사용한다. Lighthouse/TBT·field INP·서버 부하·실물 모바일·실제 OS 폴더 성능은 미측정이다.

## 연결된 목록의 작업 비용

[기존 선택 기준선](../file-change-plan/selection-after/checks.json) → [이번 선택 회귀](selection-regression/checks.json). 동일 결정적 OPFS·390x1000·3회, CDP click + React commit + DOM polling이며 실제 INP가 아니다.

이후 중앙값이 증가했지만 범위가 겹치며 표본3개로 원인을 분리하지 못한다. 임의 허용률이나 성능 개선율을 만들지 않는다. 1,000개 DOM 선택의 실제 사용자 지연은 향후 대표 기기에서 별도 검증해야 한다.

새 검색의 첫 기준선은 [검색 첫 실행](browser/checks.json)에 있다. 입력 후 한 건으로 좁히기3회, CDP 입력 전달 + 필터 + React commit + polling이고 검색 지우기는 표본 밖이다. 100개 **10.07 [8.75–16.09]ms**, 1,000개 **20.86 [15.59–45.53]ms**, 1,001개 중 표시1,000개 **16.36 [16.31–19.84]ms**. 이 표본에서 검색에 따른 추가 열거0을 확인했다. [최종 재실행](final/checks.json)의 별도 표본도 보존하며 좋은 값만 골라 합치지 않는다.

초기 로딩과 연결된 파일 동작은 다른 측정이다. 개인 문서·본문 검색·AI 전송·실제 파일 이동/복사 성능으로 일반화하지 않는다.
