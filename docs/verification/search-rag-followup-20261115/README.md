## 1. 제품의 저장 조건을 맞춘 배포 Worker 비용

이전 실험은 캐시 적중에도 본문을 저장했지만 제품 `source-snapshot.ts:278`은 `!content.cacheHit`일 때만 저장한다. 이전 224개 관측은 해당 조건의 기록으로 남기고 제품 비용 결론에서는 제외했다. 새 검사에서 이전 자료의 저장 112회가 기대 32회와 다르다는 실패를 먼저 확인했다(`cache-policy-regression-red.log`).

실제 Vercel 페이지가 쓰는 공개 Worker 자산 6개의 SHA-256을 다시 확인하고 그 **배포 native Worker**로 재측정했다. 제품과 같은 적중 시 저장 생략, 동일 File·원본 hash·전체 추출 텍스트·질문별 발췌, 캐시 유무 순서 교대, 4종 MD/PDF, Worker 신규/재사용, 변경 유무, 7회를 적용했다. 합계 224관측/112쌍, 캐시 조회 112회·저장 32회·적중 80회다. 무캐시의 파생 본문 조회·쓰기는 0회였다. 적중 80회는 저장 0회·저장 시간 0으로 확인했다.

아래는 **Worker 재사용·원본 미변경·초기 회차 제외, 각 6표본의 전체 시간 중앙값**이다.

| 입력 | 완전 무캐시 | 적중 시 저장을 생략하는 캐시 |
| --- | ---: | ---: |
| 짧은 MD | 0.30ms | 0.65ms |
| 긴 MD | 2.65ms | 3.35ms |
| 1쪽 PDF | 82.95ms | 1.05ms |
| 24쪽 PDF | 103.75ms | 1.25ms |

MD는 이번 환경에서 0.35~0.70ms의 조회·복제 비용이 더 들었고 PDF는 재추출 생략 이득이 컸다. 앞선 수치와 실행 시점·호스트 부하도 다르므로 시간 차이를 저장 조건 하나의 효과로 계산하지 않는다. 단일 기기·합성 메모리 File·공유 HTTP 캐시 조건이다. 원본 파일 시스템 I/O, 폴더 탐색·목록 저장·권한 재검사 전체, 첫 HTTP cold·CDN 요금·전체 RAM·배터리·서버 CPU를 측정한 것이 아니다. 현재 소스 `LocalTextIndex`를 별도 합성 DB에 묶어 Worker/추출 캐시 경계만 비교했다. native Worker 내부 읽기/hash/추출 호출 횟수는 직접 계측하지 않았다.

원자료: `.omx/verification/search-rag-followup-20261115/{deployed-assets,cache-corrected,cache-corrected-summary}.json`. 모든 조건의 평균·중앙값·모분산·범위와 단계별 시간은 summary에 있다. 검사: `tests/browser/check-cache-corrected-results.mjs <새 결과 JSON>`.

## 2. 같은 자료의 단어·의미 근거가 사라지는 문제

제품 `findSourceDocuments()`는 기본 검색 결과를 얻은 뒤 의미 후보를 경로로 합친다. 기존 코드는 같은 경로가 이미 있으면 의미 후보를 전부 버렸다. 문서는 중복되지 않았지만 의미 점수·본문 위치·추가 발췌가 사라졌다.

`mergeFindDocuments()`를 기존 검색 순위 모듈에 두고 제품과 평가기에서 공유한다. 기본 finding·날짜·선택 자격을 유지하며 의미 retrieval과 서로 다른 발췌를 보존한다. `retrieval.lexical: true`로 함께 발견한 후보를 구별하고, 기본 검색의 이름/경로/본문 우선순위는 그대로 유지한다. 의미 전용 후보끼리는 여전히 의미 점수로 정렬한다. 본문 미확인 후보는 의미 후보를 합친다는 이유로 선택 가능하게 만들지 않는다.

12개 근거 상한에서도 첫 기본 근거와 첫 별도 의미 근거를 먼저 남긴다. 기본 근거가 이미 12개인 경계는 리뷰에서 발견했으며, 별도 실패 회귀→수정→통과를 확인했다. 실제 companion query가 snapshot reader로 전달되는 통합 검사도 추가했다. 저장 벡터·모델 계산·스키마는 바꾸지 않아 재색인이나 모델 버전 변경이 필요 없다.

실제 로컬 모델과 OPFS 자료 한 개를 연결한 화면에서 결과 한 행, 점수 약 0.9007, `lexical: true`, “단어·의미 검색에서 함께 찾음”을 확인했다. 키보드 검색과 390/768/1440/1920px DOM의 가로 넘침 없음·선택 가능 상태를 확인했다. Ego 화면 캡처는 HMR 탐색 대기 상태에서 두 번 제한 시간을 넘겼다. 이를 시각 캡처 통과로 보고하지 않는다.

읽을 코드 순서:

1. `connection-session.ts`의 `findSourceDocuments`: 현재 원본 snapshot과 의미 결과를 얻고 합친다.
2. `search/documents/document-find-ranking.ts`: 경로 병합·근거 상한·기존 순위를 보존한다.
3. `DocumentFindResults.tsx`: 하나의 자료에 두 검색 근거를 표시한다.
4. `document-find-merge.test.ts`, `connection-session.test.ts`: 비선택 후보·상한·입력 불변·실제 호출 인자를 검증한다.

## 3. 오답·누락 실험은 개선이 없어 채택하지 않음

새 합성 v3는 20문서·16질문, seed `2026111503`, dev8/holdout8이며 문서 계열을 분리했다. 원문·정답·금지 후보·문턱 0.85·채택 조건을 실행 전에 해시로 고정했다. 직접 작성한 합성 평가이며 독립 외부 벤치마크가 아니다. 제목이 비슷하지만 본문은 무관한 자료, 제목이 약한 본문 정답, 관련 자료 없는 질문, 형식·경로·제외 조건을 포함한다. 여러 정답·제목만으로 관련성을 보완하는 자료의 충분한 품질 평가는 아직 없다.

변수 하나만 바꿔 현재 제목/경로+본문과 본문만 사용하는 임베딩 입력을 비교했다. dev에서 Recall/MRR 감소·오답 증가가 없어야 하고 적어도 하나의 엄격한 개선이 있어야 채택하도록 미리 정했다. **두 방식의 dev Recall@5/MRR은 모두 1/1, 지정 오답 1회, 관련 자료 없는 질문 후보 0개로 같았다. 개선이 없어 본문만 쓰는 방식을 거절했다.**

그 결정 뒤 현재 방식만 새 holdout에서 한 번 확인했다. 양성6질문의 Recall@5/MRR 1/1, 지정 오답 1회, 빈 질문 후보 0개였다. 그 결과로 조정하지 않았다. 기존 v2 holdout 회귀는 0.875/0.8611, 지정 오답 4회로 그대로다. 즉 **근거 합치기 오류는 고쳤지만 모델의 오답·누락을 해결했다고 주장하지 않는다.** 기존 임계값·순위 가중치·표현 버전·모델·패키지는 유지한다.

근거: `tests/fixtures/local-rag-search-v3.json`, `frozen-quality.json`, `quality-dev.json`, `quality-holdout.json`. 개발/holdout 실행은 별도 함수로 나눴고, 선택 시간보다 holdout 실행 시간이 뒤인지도 검사한다. 원래 h12의 기본 검색어 수 제한 오류와 의미 모델의 누락은 구분했다.

## 4. 긴 문서·여러 자료 RAG 13검사

실제 제품 UI·현재 원본 읽기/hash Worker·PDF.js·OPFS를 사용하고 답변 공급자만 합성 함수로 대체했다. 원본은 긴 MD 171,065bytes, 상충 날짜가 있는 MD 136bytes, 24쪽 PDF 93,976bytes다. 질문에 따라 각각 214/64/315자, 합계 593자의 발췌가 선택됐다.

- 긴 MD 뒤쪽의 날짜가 발췌되고 전체 hash와 발췌 hash가 구별됨
- 3개 경로·hash가 유지되고 실제 PDF 24쪽 추출 완료·후반 `page23` 발췌 확인
- 서로 다른 날짜가 각각의 발췌에 남음
- 별도 동의 전 action 호출 0회·전송 비활성, 전체 원문 전송으로 표시하지 않음
- 합성 답변의 세 인용이 선택 자료의 실제 발췌에 속함
- 자료에 없는 질문으로 바꾸면 동의가 풀리고 인용 없는 합성 응답을 처리함
- 준비 뒤 원본을 바꾸면 이전 발췌가 추가 action에 전달되지 않음
- 제품 코드의 원본 쓰기 0회

이것은 긴 자료의 준비·전송 범위·동의·인용·변경 차단 검증이다. 합성 답변이므로 실제 LLM의 상충 근거 판정이나 근거 없는 질문에 대한 답변 품질을 검증한 것은 아니다. 이번 추가 유료 호출은 0회이며 앞선 본문 1회 승인은 다시 사용하지 않았다. `long-rag-final/long-multi-evidence.json`과 `tests/browser/check-grounded-chat.mjs --long-multi`를 참조한다.

## 운영 배포와 실제 검색 확인 — 2026-11-15

사용자의 배포 요청으로 검토한 소스·테스트·검증 문서 26개를 일반 커밋·푸시했다. 배포 전 `pnpm check`가 schema validate·타입·린트·전체1,515단위·서버/기능 경계·빌드를 다시 통과했다. 두 대형 개인 기록 MD와 `.omx` 원자료·환경 파일은 커밋에 포함하지 않았다.

기능 커밋: [2a10c9c](https://github.com/sabin1108/file_moa/commit/2a10c9c461cae7a28ae251a4e7f3c9353886c821). [Vercel 배포](https://vercel.com/sabins-projects-011c6dea/web/2v6MBWbRQBzHhXjfGahp4A5eLdy5)의 관측 시점에 Production·Ready·Current, 동일 SHA와 운영 도메인을 확인했다. 운영 주소는 [모아](https://web-eight-rho-72.vercel.app/)다.

운영 페이지에서 별도 OPFS 합성 폴더와 한 파일만 연결했다. 선택 모델을 설치하고 그 한 파일만 준비한 뒤, 필수 검색어와 의미 설명을 직접 확인해 검색했다. 결과 한 행에 “단어·의미 검색에서 함께 찾음 · 필수 조건 확인 · 본문 1~63자”가 표시됐고 가로 넘침은 없었다. 이는 실제 배포 UI·Worker/WASM·현재 원본 확인·병합 경로의 검사이며 원격 AI 질문/답변 호출은 0회다. OS 폴더 선택은 검증용 OPFS picker로 대체했다.

검증 후 합성 연결과 폴더를 제거하고 기존 연결 3개의 활성 상태를 포함한 메타데이터 일치를 확인했다. 시작 당시 모델 Cache는 존재하되 키가 0개였으며, 검증에서 추가한 공개 모델·실행 파일·설치 표시 7개 키만 제거해 원래의 빈 Cache 상태로 되돌렸다. 기존 파일과 다른 Cache·연결은 유지했다. 해당 기능의 운영 확인과 문서 기록 뒤 최종 배포 관측은 로컬 `.omx/verification/search-rag-release-20261115/` 및 개인 인수인계에 추가한다. 의미 모델의 지정 오답4회와 누락이 해결됐다는 뜻은 아니다.
