# 긴 코드 줄 가독성 정리 — 2026-11-07

사용자가 지목한 로그인 페이지와 다른 파일의 지나치게 긴 줄을 선별하여 포맷했다. 짧은 파일 전체를 다시 포맷하거나 새 함수/공통 계층을 만들지 않았다. 제품 기능·디자인·의존성·모델 지침 원문을 바꾸지 않았다.

## 범위와 결과

| 항목 | 결과 |
| --- | --- |
| 대상 | apps/web/src의 TS/TSX 100파일 |
| 선별 | 주석/단독 문자열/import를 제외한 180자 초과 코드 줄 212개 |
| 적용 | 긴 줄마다 해당 구문 범위만 포맷, JSX/타입/조건/콜백/호출의 포함 관계 표시 |
| 남은 180자 초과 코드 형태 | 모델 지침 문자열을 선택하는 분기 1개, 정규식 1개 — 원문 유지 |
| 순증 줄 수 | 4,372 — 압축된 JSX/속성/구문을 펼친 결과이며 기능 추가가 아님 |
| 실행 구조 비교 | 100/100 변경 전후 일치 |

선별 기준은 이 작업 범위를 좁히기 위한 값이다. 100자는 포맷 목표 폭으로 사용했지만 긴 문자열·URL·정규식은 기계적으로 쪼개지 않았다. 짧은 파일, CSS, JSON, 테스트, 생성 파일에는 포맷을 적용하지 않았다. 구문 범위에 들어간 짧은 자식 속성/선언은 함께 정돈될 수 있다.

주요 변경은 [로그인 page](../../../apps/web/src/app/login/page.tsx), 인증 폼, 채팅/자료 패널, 파일 탐색·계획·복구 화면, 샘플 화면과 활성 시안의 과밀한 JSX다. 긴 함수 매개변수·검증식·객체도 선별 범위에서 정리했다. 실제 파일 목록/전후 줄 수/hash/AST 결과는 [format-report.json](format-report.json)을 따른다.

로그인 페이지는 하단 GuestSessionObserver import를 다른 import 바로 뒤로 옮겼다. import끼리의 상대 순서는 유지했다. 긴 함수 입력 타입과 notice 삼항식, return JSX를 나누고 간단한 GuestSessionObserver·filter 표현은 한 줄로 남겼다.

## 변경을 줄인 방법

[사전 계획](../../planning/long-line-readability.md)과 설치된 Prettier 3.7.4를 사용했다. 첫~마지막 긴 줄 전체를 포맷하던 제안은 서비스 본문까지 불필요하게 확장되어 버렸다. 최종안은 긴 줄을 하나씩 처리한다. 예를 들어 connection-session은 세 구문만 바뀌어 825→841줄, copy-execution은 긴 함수 선언/기본 인자만 정리해 120→130줄이다.

복잡한 JSX return 하나는 구문 전체의 들여쓰기/속성을 정리해야 하므로 줄 수가 늘어났다. 별도의 읽기 전용 제안 검토에서 이 차이와 import 순서·공백 보존을 확인했다. 활성 prototype 25파일도 과밀한 JSX가 있어 포함했으며 시안 기능을 삭제하거나 재디자인하지 않았다.

새 패키지나 포매터 설정을 추가하지 않았다. 문자열 내부 자동 포맷도 끄고 이번 선별 범위에만 일회성으로 적용했다. 기존 미커밋 내용은 .omx/readability-format/before에 먼저 보존하고, 적용 직전 원본 SHA-256이 같은지 검사했다.

## 동작 보존 검사

변경 전후 TypeScript/JSX를 JavaScript로 컴파일한 다음 AST에서 실행문/자식 순서, import 상대 순서, 문자열/숫자, 연산자, 변수 선언 종류, template rawText를 비교했다. 불필요한 괄호만 정규화했다. 값·조건 반전·문자·호출 순서·선언 종류가 달라지면 비교가 실패하는 자체 검사도 실행했다.

일반 JSX 줄바꿈은 하나의 문자열 자식을 여러 조각으로 만들 수 있다. 차이를 허용하는 예외를 넣는 대신, 해당 9파일의 단일 줄 텍스트를 명시적 문자열 표현식으로 보존한 뒤 다시 포맷했다. 37개 텍스트 노드의 공백/자식 값을 유지해 최종 100개 실행 AST가 일치했다.

타입 전용 구문·주석은 실행 AST 비교 대상이 아니다. 이를 포함한 컴파일·린트를 별도로 통과했다. AST 일치를 모든 가능한 관측값(예: 함수의 소스 문자열이나 stack line 번호)까지 같다는 형식적 증명으로 해석하지 않는다. 소스 줄 번호와 포맷에 의한 파일 hash는 바뀐다.

모델 정책의 소스 파일 hash도 포맷 때문에 달라지지만 지침 문자열·설정·실행 구문은 같다. 따라서 과거 실제 모델 원자료를 덮어쓰거나 새 정책 평가처럼 재집계하지 않았다. 새 Gemini/API 호출은 0회다.
