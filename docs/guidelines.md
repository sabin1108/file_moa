# 개발 주의사항과 원문 적용 판단

## 작성 언어 — 2026-11-08 사용자 요구

답변·문서·코드 주석에 한자와 중국어·일본어 표현을 사용하지 않는다. 전문 용어는 일반적으로 통용되는 한국어 또는 영어로 작성한다. 기존 코드 주석도 같은 규칙을 적용하며 의미를 유지해 수정한다. 테스트 설명과 임의로 만든 자료 이름도 한국어 또는 영어로 작성한다.

## 구현 설명의 대상과 깊이 — 2026-11-07 사용자 정정

“어떤 함수/방식으로 해결했는가”라는 질문은 해당 구현의 코드 흐름과 해결 원리를 이해하려는 요청이다. 사용자가 예시로 언급한 callback·searchParams 등에 설명 범위를 한정하지 않는다. 실제 관련 함수/API를 선택한 이유와 호출·입출력·상태 변화, 변경 전후의 인과관계를 쉬운 개념 설명 및 필요한 실제 코드와 연결한다. 상세 설명 규칙은 루트 AGENTS.md의 ‘구현 원리 설명’을 따른다.

기능을 읽을 때는 [코드 실행 흐름 안내](코드_이해하기.md)처럼 페이지 진입/사용자 행동에서 출발한다. 실제 식과 분기를 읽고 호출한 함수 안으로 들어간 뒤, 반환값이 호출자와 화면에 어떻게 반영되는지 돌아와 설명한다. import·문법·함수 목록은 이 흐름을 이해하는 데 필요한 경우에만 덧붙인다.

## 탐색 UI 최신 적용 — 2026-11-07

사용자 최신 요청으로 폴더 구조를 공통 왼쪽 사이드바에 표시하고 대화 자료 창은 필요할 때 연다. 과거 사이드바 구조 중복 금지/원형 메뉴 후속 기획은 이 범위에서 갱신되었다. 빠른 메뉴는 폴더·채팅·설정3개, 원본 작업이나 전송은 실행하지 않는다. 실제 연결과 샘플은 공통 표시를 재사용하지만 서로 다른 소유자/핸들/저장소 경계를 지킨다. [현재 계약](specs/workspace-navigation.md).

## 서버 통신과 데이터 책임 — 사용자 요구 2026-10-27

2026-11-09 일반 채팅 스트림 예외: 사용자가 생성 도중부터 답변을 받는 방식을 선택했다. `features/conversation-workspace/services/chat-stream.ts`만 같은 origin의 `POST /api/chat`을 직접 호출한다. 해당 Route Handler는 서버 서비스로 위임하며 인증·Origin·입력·소유권·중복·공유 한도를 검증하고 공급자 이벤트를 최소 대화 이벤트로 변환한다. 이 예외는 외부 AI 직접 호출이나 다른 업무 API의 fetch를 허용하지 않는다. 나머지 요청은 아래 Server Action 계약을 유지한다. [일반 채팅 명세](specs/general-chat.md).

2026-11-06 인증 예외: 사용자 진행 지시에 따라 `/api/auth/[...all]`만 Better Auth 이메일 인증 프로토콜의 Route Handler로 연결했다. 경로·메서드는 `src/server/auth-handler.ts`의 허용 목록으로 제한하며 업무 요청을 일반 API로 확대하지 않는다. 후속 로그인 화면의 명시적 요청은 Server Actions에서 같은 auth API를 호출하고 쿠키를 전달한다. 이메일 callback은 외부 링크이므로 GET을 유지한다. [명세와 검증](specs/auth-database-design.md).

사용자 기준: **“프론트엔드에서는 절대 API 데이터를 가공해서는 안 된다.”** 이를 서버가 반환한 업무 데이터의 의미·권한·정합성을 프론트엔드가 재정의하지 않는 계약으로 적용한다. React의 고유 결함이 아니라 모든 브라우저 코드가 사용자의 통제 아래 있다는 신뢰 경계 문제다.

- 외부 API 원본 응답 정규화, 필드 조합, 집계/가격/할당량 계산, 소유권 필터링, 승인/접근 가능 여부 결정, DB 모델→화면 DTO 변환은 서버 전용 계층에서 끝낸다. 클라이언트는 전달받은 읽기 전용 표시 DTO를 렌더링한다. 권한 없는 데이터를 일단 보내고 화면에서 숨기는 방식은 금지한다.
- 클라이언트가 맡는 것은 표시·입력·초점·접힘·선택 같은 UI 상태다. 단순 날짜/숫자 표시 형식은 업무 값 변경과 구분하되, API 데이터의 의미를 바꾸는 변환은 서버로 이동한다. 서버 작업에 영향을 주는 모든 입력/선택은 서버에서 다시 검증한다. TypeScript readonly나 클라이언트 입력 검사는 보안 통제가 아니다.
- 브라우저에서 시작하는 제품 업무 요청의 진입점은 `src/app/actions/`의 Server Actions로 제한한다. UI/hook/클라이언트가 가져올 수 있는 일반 모듈의 직접 fetch·XHR·WebSocket·EventSource·외부 API SDK·서버 DB SDK 접근은 금지한다. Next 자체의 RSC/탐색/Action 전송은 프레임워크가 담당하며 이 금지의 대상이 아니다.
- 초기 조회는 Server Component → `src/server/`의 데이터 접근/서비스를 사용한다. Server Component가 자기 HTTP API나 Action endpoint를 다시 호출하지 않는다. 서버 Action은 브라우저에서 시작한 명시적 작업의 진입점이며, 일반 조회를 모두 Action으로 우회시키지 않는다. 필요 시 명시적 조회 Action도 같은 서버 검증/최소 DTO 계약을 지키되, Action 큐의 직렬 실행 비용을 측정한다.
- `src/server/`의 외부 접근·환경변수·DB 스키마·서버 업무 규칙에는 `import "server-only"`를 둔다. `src/app/actions/`는 파일 맨 위 `"use server"`와 `import "server-only"`를 사용하고 검증된 서버 서비스를 호출한다. Action에 DB/외부 fetch/비밀키 처리를 몰아넣지 않는다. `use server`는 임의 서버 유틸리티를 표시하는 용도가 아니다.
- Action마다 인증 세션, workspace/리소스 소유권, 런타임 입력, 필요한 멱등성/비용 제한을 검증한다. 페이지의 인증 검사나 보이지 않는 버튼, Action ID의 추측 어려움을 권한 근거로 삼지 않는다. Origin/CSRF 기본 보호를 유지하고 프록시·허용 origin 설정은 실제 배포 환경에서 검증한다.
- 비밀키·DB URL·OAuth access/refresh token은 서버에만 보관한다. NEXT_PUBLIC_*·next.config의 env·JS 번들·props·RSC·Action 반환값·오류·로그에 넣지 않는다. 세션 쿠키는 인증 구현 시 HttpOnly/Secure/SameSite 정책을 갖춘다. HttpOnly는 페이지 JS의 읽기를 막으며 기기 소유자의 DevTools 열람까지 막지 않는다.
- F12에서 브라우저 요청·응답·화면 데이터·Action 호출·로컬 저장소는 보인다. 이를 숨긴다는 보안 목표를 세우지 않는다. 서버 DB 스키마/비밀 자격증명을 보내지 않고, 서버가 허용한 최소 데이터만 전달하는 것이 목표다. 로컬 IndexedDB의 연결 저장 구조는 사용자 브라우저 저장소이므로 서버 DB와 구분한다.
- 현재 로컬 폴더의 권한 요청·핸들·목록·로컬 표시 정렬은 브라우저 전용 책임이다. 서버 API 응답을 가공하는 동작이 아니며 Server Action으로 옮기거나 원본을 자동 업로드하지 않는다. 향후 전송은 사용자가 확인한 자료만 허용하고 서버는 그 내용을 다시 검증한다.
- `/api/health`는 민감값 없는 운영 상태 확인으로 유지한다. OAuth callback/webhook/실시간 스트림은 외부 프로토콜이므로 Action으로 무조건 대체할 수 없다. 현재 예외는 위 인증 경로와 일반 채팅 스트림이며, 추가 경로는 별도 명세·보안 검토·사용자 범위 합의 후 정한다. 기존 POST+fetch SSE 초안은 다른 브라우저 직접 호출의 허용 근거가 아니다.

자동 검사: `pnpm lint`는 서버 경계 표식·직접 통신·SDK/환경변수 접근 패턴을 검사하고 `pnpm test:boundaries`는 위반/허용 예제를 검사한다. 정적 규칙은 우회 불가능한 보안 장치가 아니며 DTO 내용이나 권한 로직의 정확성을 증명하지 않는다. 실제 서버 기능이 생길 때 A/B 사용자 교차 접근·위조 ID·변조 입력·비밀 응답 부재 테스트와 클라이언트 번들/네트워크 검사를 추가한다. 현재 인증/서버 DB/AI 연동은 미구현이다.

근거: 설치된 Next16.4.3의 data-security/server-and-client-components/fetching-data 가이드 및 [공식 보안 문서](https://nextjs.org/docs/app/guides/data-security), [서버 액션의 용도/큐 제한](https://nextjs.org/docs/app/guides/backend-for-frontend#server-actions).

## 사용자와 함께 검토하는 개발 — 2026-10-25

- 사용자는 코드 구조와 구현 과정을 직접 읽고 검토하기를 원한다. 기능 하나를 작은 검토 단위로 나누고, 각 단위의 구현·필요한 검증·설명을 마친 뒤 사용자 검토를 받는다. 다음 단위는 사용자의 검토 또는 진행 지시 후 시작한다. 이것은 사용자가 요청한 작업 방식이며 일반적인 반복 승인 요청으로 확대하지 않는다.
- 시작할 때 이번 단위의 사용자 동작, 변경할 책임, 완료 조건을 짧게 밝힌다. 단위 안의 읽기·수정·오류 수정·검증은 스스로 끝낸다.
- 보고에는 읽을 파일 순서, 각 파일의 역할, 입력→처리→결과, 변경 이유, 직접 확인하는 방법, 실행한 검증과 미검증 범위를 담는다. 구현 전 설명과 실제 완료를 구분한다.
- 기존 기능 폴더·컴포넌트·토큰을 먼저 사용한다. 새 파일은 책임이나 실제 재사용 이유가 있을 때 추가하며, 리뷰할 때 그 이유를 설명한다. 사용자 검토 요청을 전체 구조 정리나 대규모 리팩터링 허가로 확대하지 않는다.
- 해당 기능의 프로젝트 스킬과 명세·실패 테스트·검증 지침을 적용한다. 성능 처리는 측정 근거를 따르며 미래의 사용을 추측해 범용 계층을 늘리지 않는다.
- 최신 단계의 안내는 하나의 기능 명세에서 관리한다. 같은 계획을 여러 새 문서로 복제하지 않는다.

## 사람이 읽는 코드와 배포 전 임시 코드 — 2026-10-26

- 한 줄에 준비·실행·검증이나 여러 상태 변경을 몰아넣지 않는다. 여러 분기의 삼항식은 이름 있는 값이나 if/else로 풀고, 긴 JSX의 속성·조건·내용은 줄을 나눠 읽게 한다.
- 함수·변수·테스트 이름은 무엇을 하는지 설명한다. 짧은 약자보다 구체적인 이름을 쓰고, 한 함수의 입력 → 처리 → 결과가 이어져 보여야 한다. 파일 수나 줄 수 감소를 가독성으로 착각하지 않는다.
- 테스트도 사용자에게 설명할 코드다. 준비 → 실행 → 확인을 구분하고, fake/mock/deferred가 무엇을 대신하는지 주석으로 밝힌다. 테스트 하나의 주장과 검증하지 못하는 외부 경계를 함께 설명한다.
- 개발 전용 소유자·DB·localhost 제한·합성 데이터에는 `TEMPORARY(local-folder-dev)`처럼 검색 가능한 주석을 붙인다. 이유, 배포 전 교체 대상, 완료 조건을 해당 기능 명세 한 곳에 기록한다. 만료 조건 없는 TODO만 남기지 않는다.
- 개발용 표시 제거와 기능 교체를 구분한다. 현재의 고정 개발 소유자/별도 DB/localhost 제한은 실제 인증·세션 연결 후 교체하고 개발 안내 문구를 제거한다. 지원 브라우저·보안 컨텍스트 검사, 권한 거절·저장 실패 안내는 제품에도 필요한 동작이다. 배포를 위해 제한만 삭제하고 가짜 소유자를 그대로 사용하지 않는다.
- 임시 코드가 들어간 변경 보고와 코드 해설에는 그 위치·임시인 이유·교체 조건을 중요하게 설명한다. 개발용 연결을 실제 사용자 계정 격리로 보고하지 않는다.
- 프로토타입은 기능 대체와 검토 목적이 끝나면 최종 배포 전이라도 제거할 수 있다. 먼저 실제 소비처/import/경로/검토 증거를 확인하고, 제품이 쓰는 공통 표시 요소와 샘플 fixture·전용 경로를 구분한다. 재사용 중인 코드는 유지 또는 실제 공유 위치로 옮긴 뒤 참조를 갱신한다. 근거 없는 일괄 삭제·폴더 통합은 하지 않는다.

## 실제 화면에서 즉시 검증할 수 있는 기능 — 2026-10-26

- 실제 작업 경로에는 실제 입력·저장소·처리 결과만 표시한다. 합성 대화·파일·계정·숫자·타이머로 만든 진행률·가짜 성공을 채워 넣어 구현된 것처럼 보이게 하지 않는다.
- 미구현은 ‘미구현’으로 표시한다. 조회하지 않은 파일을 ‘0개’나 ‘빈 폴더’로 표현하지 않는다. 불가능한 조작으로 예시 결과를 만들지 않는다.
- 새 기능은 실제 작업 경로에서 바로 조작하고 결과·실패·재시도를 확인할 수 있게 연결한다. 문서나 시안만으로 기능 완료를 보고하지 않는다.
- 필요한 시안과 합성 테스트 데이터는 `/preview`와 검사 도구에 격리한다. 시안에는 합성임을 알리고 실제 화면으로 돌아오는 진입을 둔다. 시안 조작이 실제 저장소·권한·사용자 데이터를 변경하지 않게 한다.
- 공통 CSS·표시 컴포넌트 재사용과 합성 업무 상태의 혼입은 구분한다. 이번 경계와 현재 구현 범위는 [실제 작업 화면 명세](specs/live-workspace.md)를 따른다.

## AI 코드 리뷰의 필수 확인 세 가지 — 2026-10-26

1. **프로젝트 버전과의 일치**: `package.json`의 요구 버전, lockfile의 해석된 버전, 실제 설치 버전, 실행 환경(Node/브라우저)을 비교한다. 해당 버전의 로컬 문서·공식 변경 내역을 확인한다. 익숙한 예전 버전이나 최신 웹 문서를 그대로 적용하지 않는다. 검증하지 못한 버전·불일치를 명시하고 임의 업그레이드를 하지 않는다.
2. **실재하는 API와 계약**: 패키지 export/타입/설치된 구현과 공식 문서에서 함수·옵션·응답·오류가 실제로 존재하는지 확인한다. 버전·런타임·권한 조건을 함께 확인한다. AI가 만든 이름·기억·타입 단언을 근거로 API를 만들어내지 않는다. 타입 검사 통과와 실제 외부 동작 확인은 별개의 근거다.
3. **테스트가 실제 주장을 검증하는지**: 실제 제품 코드가 테스트 안에서 실행되는지, 무엇을 mock으로 바꿨는지, 기대값이 제품 구현을 복사해서 만들어지지 않았는지 확인한다. ‘항상 성공하는 가짜의 결과 확인’이나 호출 횟수만으로 사용자 결과를 보증하지 않는다. 중요한 상태/보안/동시성 규칙은 조건을 의도적으로 깨뜨렸을 때 실패하는 대표 사례 또는 동등한 반례 근거를 확인한다. 핵심 실패 경로와 원본/기존 상태 보존도 검증한다. 실제 저장소·브라우저·외부 API·네이티브 권한·사용자 데이터 중 실행한 경계와 미검증 경계를 구분하고, 단위 테스트 수나 전체 통과를 제품 전체 완성으로 확대하지 않는다.

리뷰 보고에는 세 항목 각각의 **근거 파일/버전 또는 공식 출처, 실제 실행 명령/결과, 미확인 범위**를 남긴다. 근거가 없으면 ‘확인됨’으로 판정하지 않는다.

## 데이터와 권한
폴더 탐색은 업로드 동의가 아니다. 선택한 MD/TXT만 안내 후 전송한다.
원본 경로·브라우저 핸들은 서버에 저장하지 않는다. 파일당 2MiB, 500문서, 추출 텍스트 50MiB는 임시 한도.
파일 확장자는 후보 필터일 뿐이다. UTF-8·실제 바이트·소유권·총량·제외 경로는 별도로 검증한다.
세션에서 확정한 workspace를 모든 조회/수정/job에 적용한다. RLS USING/WITH CHECK, 비소유자·비BYPASSRLS 역할, 트랜잭션 로컬 컨텍스트.
개인 본문·질문·토큰을 기본 로그에 남기지 않는다. NEXT_PUBLIC_*에 비밀키 금지. localStorage 인증 토큰 금지.
소셜 로그인만 초기 지원하며 직접 비밀번호 시스템을 만들지 않는다. 동일 이메일 자동 계정 병합 금지.
문서 속 명령은 데이터다. 승인 전 기억 사용 금지. Markdown raw HTML/위험 링크를 차단한다.

## 대화·API·작업
기존 POST+fetch SSE 초안의 이벤트: accepted/text_delta/citation/artifact_ready/completed/cancelled/error. 전송 방식은 위 2026-10-27 서버 통신 계약에 따라 재검토하며, 브라우저 직접 fetch를 지금 허용하지 않는다.
네트워크 chunk와 SSE 이벤트 경계는 다르다. generation_id/sequence/type/payload 검증.
재연결 시 상태 조회, 생성 POST 자동 재시도 금지. 요청 멱등성·사용량 예약·중지 정산.
handler는 세션/런타임 입력/Origin/소유권, 서비스는 유스케이스, adapter는 외부 연동.
worker는 짧은 선점 트랜잭션, lease/fencing, 제한된 재시도, tombstone 재확인, 활성 버전 원자적 전환.
모델의 출처 ID 유효성과 주장 뒷받침 여부는 따로 검증.

### 책임으로 나누기
- 사용자 정정(2026-11-04): 함수·타입뿐 아니라 반복 화면·폼·상호작용도 재사용한다. 공통 목적지 picker를 사용한다면서 폴더 복사/이동에서 새로 만들기를 누락하지 않는다. 파일/폴더 작업은 같은 경로 입력·탐색·새 항목 생성·검토 UI를 공유하고 기능 차이는 실제 제약이 있는 설정값으로만 표현한다. 공통 Stepper는 단계 데이터에 독립적인 표시 컴포넌트로 두어 파일 작업/후속 로그인·회원가입에서 재사용한다.
- 페이지/상위 화면은 배치와 조합을 맡는다. 입력 UI, 메시지 목록, 파일 트리, 미리보기처럼 독립적인 역할은 이름 있는 컴포넌트로 나눈다.
- 화면 표시와 상태 전이, 네트워크 호출, 파일 접근, 업무 규칙을 하나의 컴포넌트나 거대한 hook에 모으지 않는다.
- React 상태/수명주기와 관련된 로직은 역할이 드러나는 hook/reducer로, React와 무관한 검증·변환은 순수 함수로 분리한다. hook 내부에 업무 규칙을 숨기지 않는다.
- 서버 handler는 요청 경계, service는 유스케이스, adapter/repository는 외부 접근을 담당한다. 단순한 처리에 전달만 하는 계층을 추가하지 않는다.
- 컴포넌트를 나눠도 초안·선택·스크롤의 소유권은 유지한다. 불필요한 전역 상태나 중복 상태로 연결하지 않는다.

### 찾기 쉬운 구조
- 기능별 폴더에 컴포넌트·hook·스타일·테스트를 가까이 둔다. 실제로 여러 기능이 쓰는 코드만 shared/domain으로 올린다.
- feature 내부 구현을 다른 feature에서 직접 가져오지 않고 명시된 진입점/계약을 사용한다. 순환 의존성을 만들지 않는다.
- 파일명과 함수명으로 역할을 표현한다. 관련 없는 로직을 utils.ts, helpers.ts, common.ts 한 파일에 계속 쌓지 않는다.
- props, DTO, 이벤트, 반환 타입으로 경계를 드러내고, 외부 입력은 런타임 검증한다. 타입 단언이나 any로 불일치를 덮지 않는다.
- 사용자 추가 기준(2026-10-28): TypeScript의 `any`는 꼭 필요한 경우에만 사용한다. 구체적인 타입·유니온·제네릭을 우선하고, 알 수 없는 외부 값은 `unknown`으로 받아 런타임 검증과 타입 좁히기를 거친다. 불가피한 외부 라이브러리 경계 등의 예외는 범위를 최소화하고 필요 이유를 주석과 리뷰에 남긴다. `as unknown as T`나 검사 무시 지시문으로 같은 문제를 우회하지 않는다.
- 주석은 코드의 반복 설명보다 선택 이유·제약·예외를 설명한다. 사용자에게 보이는 실패 상태와 복구 동작을 코드에서 찾을 수 있게 한다.
- 사용자 추가 기준(2026-10-28): 구조와 소유권으로 해결할 문제를 조건문·중복 상태로 덮지 않는다. 변경 시 진입점→화면 조합→상태→규칙/외부 접근의 실제 파일 경로와 리뷰 순서를 [코드 안내](code-map.md)에 연결한다. 핵심 경계에는 역할·호출 흐름·보안상 이유를 설명하는 주석을 남긴다.

### HTML 의미와 콘텐츠 모델
- 문단은 p, 행동은 button, 이동은 a/Next Link, 목록은 ul/ol과 li, 이름/값은 dl·dt·dd, 독립 문서는 article을 우선한다. 의미가 없는 배치 그룹에는 div를 써도 된다. section에는 식별 가능한 제목 또는 이름을 준다.
- p 내부에 div·목록·section 같은 비구문 콘텐츠를 넣지 않는다. button은 구문 콘텐츠라 p 안에서 무조건 금지되는 것은 아니지만, 버튼/링크 안에 다른 상호작용 요소를 중첩하지 않는다. 브라우저가 잘못된 HTML을 복구해 보인다는 이유로 허용하지 않는다.
- 네이티브 버튼의 type, 링크의 href, disclosure의 aria-expanded/aria-controls, 페이지의 main/lang, 키보드 초점과 숨김 상태를 검토한다. ARIA로 잘못된 네이티브 구조를 덮지 않는다.
- JSX 소스와 실제 DOM을 함께 확인한다. lint·DOM 선택자 검사는 전체 HTML 적합성/접근성 인증이 아니며, custom component가 펼쳐진 결과와 조건부 상태도 검토한다.

### 분리 판단
줄 수만으로 기계적으로 쪼개지 않는다. 서로 다른 변경 이유가 섞이거나, 독립 테스트가 어렵거나, 여러 상태 흐름 때문에 이해가 어려워지면 분리한다.
반대로 한 번 쓰는 짧은 표시 코드를 모두 별도 파일로 나누거나, 미래를 위한 범용 프레임워크·빈 계층을 만들지 않는다.
예: ConversationShell은 상태 소유와 조합, MessageList는 메시지 표시, Composer는 입력 UI, useChatStream은 스트림 연결/해제, stream parser는 순수 파싱을 맡는다. 이는 향후 책임 예시이며 현재 구현된 파일 목록은 아니다.

### 리뷰 가능한 변경과 증거
- 변경 하나에 하나의 목적을 둔다. 기능 변경과 무관한 파일 이동·서식 변경·리팩터링을 섞지 않는다.
- PR/작업 보고에 문제와 변경 후 동작, 읽을 파일 순서, 각 파일의 역할, 중요한 선택 이유, 검증 명령/결과와 미검증 범위를 남긴다.
- 테스트는 책임 경계와 사용자 행동을 검증한다. 단순 구현 복제 테스트보다 오류·취소·권한·상태 전이의 회귀를 막는다.
- 리뷰 체크: 책임 혼합 여부, 상태 소유권, 의존 방향, 명시적인 입출력, 실패 처리, 불필요한 추상화, 관련 테스트, 변경 범위.
- 주요 구조/계약 변경은 architecture 또는 ADR에 근거를 기록한다. 자동 검사가 통과해도 사람이 이해하기 어려운 구조가 정당화되지는 않는다.

- 동일 행동의 라벨·높이·색·아이콘·focus·비활성 상태를 공통 컴포넌트/variant로 유지한다. 버튼·링크·상태 표현은 components/ui의 actionClasses/ActionLink/StatusLabel 및 styles/controls.module.css를 재사용한다. PreviewButton은 prototypes 전용이다.
- 공통 디자인은 실제 반복을 기준으로 추출한다. 재사용을 이유로 서로 다른 도메인 책임을 거대한 만능 컴포넌트로 합치지 않는다.
- 읽기 면/탐색 면/선택 면과 text/muted/border 토큰을 분리한다. 긴 본문은 16–17px, 1.8–2.0 행간, 약 620–720px 너비를 출발점으로 한국어와 200% 확대를 확인한다.
- 과도한 동일 색·동일 크기 텍스트·회색 장문을 피한다. 제목/본문/메타 위계와 충분한 문단 간격을 둔다. 자동 대비 판정은 장시간 읽기의 편안함을 대신하지 않는다.

## Lighthouse와 실제 UX 검증
- 실제 기능의 관련 UI/성능 변경은 production build에서 desktop/mobile을 측정하고 Lighthouse 버전·Chrome·실행 조건·LCP/CLS/TBT·접근성 실패·HTML/JSON을 기록한다. 정적 프로토타입은 기능/성능 테스트 대상에서 제외한다.
- 재현 스크립트 tests/performance/audit-ui.ps1을 사용한다. 가능하면 동일 조건 3회 중앙값과 이전 기준을 비교하며, 단발 점수는 baseline으로 표기한다.

## SDD·TDD 및 테스트셋
- SDD는 Specification-Driven Development로 해석한다. 사용자 결과·범위·실패·금지 부작용·완료 기준을 버전 있는 명세에 적고 변경 시 코드·테스트와 함께 갱신한다.
- 실제 기능 구현 시 spec ID → Given/When/Then → 의미 있는 실패 테스트 → 최소 구현 → 리팩터링 → 관련 검증 순서를 따른다.
- 문구/CSS 같은 저위험 변경에는 구현을 복제하는 테스트를 양산하지 않는다. 파일·권한·파서·상태 전이에는 경계값/실패 불변식을 우선한다.
- 5–15개 사람 검토 core부터 시작하고 기능별 50–100개, 이후 seed 기반 800–1,000개로 확장한다. case 수/파일 수/질문 수/실행 수를 구분한다.
- 출처·사용 조건·버전·근거·기대/금지 결과·seed·holdout을 기록한다. 공개 데이터/AI 생성셋을 무검토 golden으로 사용하지 않는다.
- 계획과 확보 방법은 docs/testing-strategy.md, 초기 12개 계약은 evals/fixtures/seed/cases.seed.json. 이는 아직 실행된 제품 테스트가 아니다.

## 사이트 전체 성능·기획 적용 — 2026-10-24
성능 범위는 채팅 지연에 한정하지 않는다. 화면별 LCP/CLS/TBT·field INP, 초기 전송량/요청 수, 공통 JS/CSS, 전체 배포 자산, 메모리/주 스레드, API/서버 비용을 기록한다.
[성능 정책](performance-policy.md)과 [수치표 양식](performance-record-template.md)이 측정 시점·비교 조건의 기준이다. 기능 추가 전 기록은 유지하고 기존 같은 흐름의 회귀와 새 기능의 비용을 분리한다.
정적 시안에는 타입·lint·build·화면 확인만 한다. 과거 Lighthouse 기록은 이전 정적 화면의 기록으로 보관하고 현재 실측처럼 인용하지 않는다.
파일 관리의 첫 뷰는 폴더가 하위 폴더와 파일을 감싸는 포함 구조. 출발/도착 폴더를 시각적으로 연결하고 공통 FolderCard를 재사용한다.
채팅 사이드바는 주 메뉴와 최근 대화 위주로 줄인다. 좌클릭 길게 누르는 메뉴는 [후속 기획](planning/radial-menu.md)만 있으며 시안에 구현하지 않는다.
## 모든 화면의 디자인 판단 기준 — 사용자 추가
AI가 만든 범용 템플릿 같은 인상을 줄이는 것을 모든 화면의 공통 기준으로 삼는다.
- 먼저 실제 대상과 사용자 행동을 정한다. 폴더는 포함 관계, 대화는 왕복 흐름처럼 대상의 구조가 화면을 결정한다.
- 장식용 카드 격자·배지·통계·자동 추천 문구·긴 사용 설명으로 빈 공간을 채우지 않는다. 폴더 경계처럼 의미를 전달하는 상자는 유지한다.
- 같은 크기의 박스를 반복 배치하기보다 내용과 작업 중요도에 맞춰 크기·여백을 정한다.
- 버튼에는 대상과 행동을 적고, 실행 전 출발/도착·예상 결과를 확인할 수 있게 한다. 아이콘과 '여기로'만으로 동작을 설명하지 않는다.
- 과장된 그라데이션·장식 효과보다 읽기 쉬운 서체, 사용자 팔레트, 실제 파일/폴더 구조를 우선한다.
- AI 티가 없다는 평가는 자동 점수로 확정하지 않는다. 시안과 사용자 피드백으로 확인한다.

### 데스크톱의 여백과 화면별 구성 — 2026-10-24
- 작은 내용을 중앙에만 놓고 나머지를 비워 두는 것을 기본값으로 삼지 않는다. 1440/1920px에서 내용이 차지하는 폭·높이, 주변 여백과 첫 화면의 행동 위치를 함께 검토한다.
- 빈 곳에 무관한 통계·카드·일러스트·안내 문구를 넣지 않는다. 이미 존재하는 문서, 폴더 계층, 출발·도착, 처리 목록, 데이터 보관 범위가 시각적인 내용을 맡는다.
- 문서에는 읽기 폭을 제한한 본문과 문서 정보, 이동에는 경로와 처리 내역, 충돌에는 동등한 비교, 검색에는 기록 목록, 설정에는 조작 결과의 작은 미리보기를 사용한다. 모든 화면에 같은 왼쪽 장식 패널을 붙이지 않는다.
- 여백을 모두 없애는 것이 목표는 아니다. 내용에 맞는 높이와 명확한 정렬선을 유지하며 짧은 상태 화면을 화면 끝까지 늘이지 않는다. 공통 버튼과 목록은 재사용하고 구성은 작업 목적에 맞춘다.
- 독립 시안 페이지뿐 아니라 실제 시안 버튼으로 여는 dialog, 좁은 화면의 읽기 순서·스크롤·초점 복귀도 확인한다. 레이아웃 검사는 디자인 승인이나 전체 접근성 인증이 아니다.

### 간격과 재사용을 먼저 정하는 작업 화면
- 화면 폭을 늘리는 것으로 밀도 문제를 해결하지 않는다. 선택한 taste 방향을 바탕으로 간격·타입·행·조작의 기준을 먼저 정하고 실제 렌더링 치수로 확인한다.
- 반복되는 값은 해당 작업 화면 범위의 CSS 토큰으로 관리한다. 승인된 다른 화면에 새 토큰을 일괄 적용하지 않는다.
- 페이지와 dialog가 같은 내용을 보여주면 제목·설명·본문·상태 안내 구조를 공유한다. 탐색 상태와 modal 초점/수명주기는 각 host가 소유한다.
- 목록과 경로 표시 컴포넌트는 데이터와 상태를 props로 받고 샘플 fixture를 직접 가져오지 않는다. 실제 API를 붙이는 작업은 화면 조합의 입력 교체가 되도록 한다. 쓰이지 않는 범용 변형은 미리 추가하지 않는다.
- 긴 파일명·경로, 좁은 화면과 확대에 해당하는 리플로, dialog 내부 스크롤·키보드 초점·재진입 상태를 확인한다. 정렬을 지키려고 필수 파일명을 잘라 숨기지 않는다.
### 경고와 권한 범위의 시각화

- 경고는 구체적인 문제, 영향받는 대상, 유지되는 범위, 다음 행동을 함께 보여준다. 상황에 맞는 비교 구획을 사용한다.
- 주의와 삭제의 의미를 색·아이콘·문구로 함께 전달한다. 일반 화면 전체를 경고색으로 칠하거나 모든 확인을 위험으로 과장하지 않는다.
- 폴더 읽기 권한과 서버 전송 동의를 분리한다. 권한 상실을 파일 삭제로 설명하지 않는다. 확인되지 않은 실패 원인·복구 가능성·실행 완료를 단정하지 않는다.
- 공통 경고 요약과 영향 비교를 재사용하되 동의 상태·비동기 처리·외부 접근은 표시 컴포넌트에 넣지 않는다.

### 상태 UI의 기능적 재사용

- 로딩·진행·답변·성공/실패 표시 계층에 샘플 데이터, scene ID, 네트워크, 타이머를 넣지 않는다. 실제 상태와 내용, 콜백을 가진 조작 요소를 입력으로 받는다.
- 최초 로딩과 갱신을 구분한다. 갱신/오류 중에는 마지막 내용과 입력을 유지한다. 화면 전체를 불필요하게 다시 마운트하지 않는다.
- 단계·진행률은 실제 작업 결과만 표시한다. 준비 완료를 애니메이션 때문에 늦추지 않는다. 동작 줄이기 설정을 존중한다.
- 부분 답변과 초안 보존은 상태 소유자의 책임이다. 표시 컴포넌트의 재사용을 서버 재시도·복원·저장 기능 구현 완료로 보고하지 않는다.
- 재사용 근거는 실제로 공유하는 호출 위치와 입력 계약으로 남긴다. 신규 표시 컴포넌트마다 가상의 범용 옵션을 미리 늘리지 않는다.

# 사용자 추가 코드 가독성 기준 — 2026-11-03

코드는 사람이 흐름을 따라 읽으며 수정할 수 있게 작성한다. 독립적인 선언과 실행문을 한 줄에 연달아 붙이지 않는다. 가드 조건, 입력 준비, 비동기 호출, 결과 확인, 상태 변경, 반환을 의미 있는 문단으로 나누고 if/try/catch의 본문은 여러 줄로 쓴다. 짧은 표현식까지 모두 별도 함수로 만들지는 않는다.

길어진 생성자·콜백·JSX 속성은 읽기 단위로 줄을 나눈다. 타입은 실제로 같은 계약일 때 재사용하고, 파일 수나 줄 수를 줄이기 위한 거대 컴포넌트나 불필요한 범용 계층을 만들지 않는다. 명시적any는 웹 소스에서 lint 오류다. 외부 입력은unknown으로 받아 검증하며 타입 단언으로 검증을 대신하지 않는다.

외부 JSON처럼 런타임 검증이 필요한 경계에서 Zod의 스키마와 추론 타입을 사용할 수 있다. 검증 형식과 타입 중복을 줄이는 이유를 기록하고, 파일 권한·크기 상한·재읽기·해시·작업 순서 계약은 별도로 유지한다. 이번 정리는 변경된 파일 기능22개에 한정했으며 전체 저장소의 모든 코드가 정리됐다는 뜻은 아니다.

사용자 보완(2026-11-07): 읽기 어려울 정도로 긴 JSX·선언·조건·호출을 선별하여 줄바꿈한다. 짧은 컴포넌트·간단한 속성식까지 억지로 여러 줄로 늘리거나 줄바꿈을 위해 함수를 추출하지 않는다. JSX 포함 관계와 속성, 여러 동작이 섞인 콜백을 읽기 단위로 나누되 문자열/정규식/SQL/모델 지침 원문과 의미 있는 공백은 보존한다. 이번 정리의 180자 선별/100자 포맷 폭은 작업 설정이며 전 코드에 강제할 불변 규칙이 아니다.
