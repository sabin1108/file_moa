# 로그인된 설정 화면의 캐시 비교

원래 지연 버전의 실행 가능한 빌드는 보존되어 있지 않다. `lpCxf_CNfziJk7VhXxTME`는 정적 산출물 메타데이터만 존재한다. 따라서 이 검사는 현재 코드의 복사본에서 캐시 도입 전 조회 방식을 복원한 비교 기준과 현재 캐시 구현을 비교한다. 당시 전체 버전을 그대로 실행한 결과로 표현하지 않는다.

두 복사본은 같은 UI·인증 정책·DB 인스턴스를 쓴다. before는 초기 layout 준비를 제거하고 설정에서 기존 세션 기반 account/connection 공개 reader를 병렬 호출한다. after는 현재 Next Data Cache와 초기 준비를 유지한다. before는 프로필을 세션에서 얻으며 after의 cache miss에는 프로필 조회가 하나 더 있다. 따라서 캐시 API 하나만의 효과로 해석하지 않는다. 제품 소스와 사용자 폴더는 수정하지 않는다.

측정은 production 빌드, 같은 브라우저·계정·네트워크에서 시행한다. 원래 앱은 3034, before는 3035, after는 3036, 결과 수집 화면은 3037이다. 두 복사본에 AI 키를 전달하지 않는다. 쿠키 원문은 읽거나 기록하지 않는다. 사용자는 현재 로그인한 브라우저에서 측정을 시작한다.

기록할 값:

- 첫 작업 공간 진입: 현재 방식의 초기 준비 비용까지 포함.
- 설정 첫 진입: 첫 설정 JS/화면 로딩 포함, 반복과 분리.
- 첫 작업 공간 진입과 첫 설정 진입의 합: 대기 시간이 초기 진입으로 옮겨간 효과까지 비교.
- 반복 설정 진입: 같은 화면의 router.push 탐색, 고유 query로 요청 강제. Link prefetch와 같은 URL의 Router Cache 재사용은 배제한 조건이다.
- 브라우저: 탐색 시작부터 설정 서버 결과가 화면에 반영된 다음 두 frame까지의 시간. 실제 사람의 체감 평가를 대신하지 않는다.
- 서버: 설정 표시 reader의 총 시간, after의 인증 구간과 callback 실행 여부. ORM 실제 round-trip 수로 해석하지 않는다.
- 각 원자료, 중앙값·p95, 표본 수와 실행 순서. 확정한 결과만 보고한다.

실제 운영 Vercel과 로컬 production은 다르다. 첫 DB 연결/브라우저 캐시, 설정 60초 재검증, 추가 SessionBoundary 검사와 네트워크 변동을 기록한다. 측정 중 다른 작업을 하거나 설정을 변경하지 않는다. 로그인·새로고침 등 예상 밖 이동 시 중단한다.

각 시작 전에 해당 측정 서버만 재시작하고 그 복사본의 Next fetch-cache를 지운다. 처음 진입의 cache miss를 확인하며 원래 앱의 캐시는 건드리지 않는다. 브라우저 HTTP 캐시는 지우지 않고 첫 시행과 후속 시행의 차이를 기록한다. before→after→after→before 순서로 측정하며, 작은 표본의 p95를 안정된 사용자 전체 지표로 표현하지 않는다. 브라우저 결과는 각 시행 종료 후 모아서 보내고 인증 쿠키는 수집 서버로 보내지 않는다.
